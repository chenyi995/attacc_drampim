# 协同 prefill（GPU+PIM，A6）何时快于纯 GPU prefill（A4）——拐点表

## 实验
回放对 workload（见 README.md）：请求 0 = sys(32) + 共享 doc(L = 8192) + query(n_new)，由 GPU 完整 prefill，K/V 留在 AttAcc HBM；请求 1 = 16 token 的独有前缀（位置偏移）+ 同一个 doc + query(n_new)，作为复用 prefill 被测。比较请求 1 的 prefill 时间：**A4** = 纯 GPU（复用 K/V 经链路读回 GPU 再算），**A6** = 协同（GPU 算新行 attention，PIM 就地扫描复用 K/V）。GPU 模型 = `--gpu-model flash`（FlashAttention-2），bank PIM，Ramulator 计时，PIM query batch 4，LLAMA-7B / 65B / 175B，8 GPU + 8 AttAcc。

## 表头含义
* **n_q**：回放请求在每个 partial 层里、必须对复用 K/V 做 attention 的 query 行数 = 本轮新 token（n_new + 16 偏移）+ 策略额外重算的行（CacheBlend 为 r·L，EPIC 为每段 p 个 token）。它决定 PIM 要把 8192 行复用 K/V 重扫几趟（⌈n_q/4⌉）。
* **拐点 n_q\***：仿真得到的 n_q 值，使 A6 时间 = A4 时间（取两侧网格点线性插值）。n_q 小于拐点 → 协同更快；大于 → 纯 GPU 更快。
* **允许的最大 r（CacheBlend）**：要让协同更快，CacheBlend 的 recompute ratio r 必须 ≤ (n_q\* − n_turn)/L；按本轮新 token 数 n_turn = 0 / 8 / 32 三种情况给出，"—" 表示这一轮即使没有新 token 也到不了拐点。
* **EPIC 的 n_q 构成**：EPIC（AttnLink）只重算每个复用段开头的 p 个 token，其余复用；n_q = p × 复用段数 + 本轮新 query token（同一 prompt 回放时没有新 query）。回放对只有 1 个复用段。
* **允许的最大重算 token 总数（EPIC）**：同一 prompt 回放（无新 query）时协同仍更快所需的 p × 段数 上限，= n_q\*；若这一轮还有新 query，则再减去新 query 的 token 数。p 越大 EPIC 精度越好，这一列就是协同方案能负担的重算预算。
* **夹逼点**：拐点两侧的仿真网格点及其 A6/A4 时间比，形如 "24: 0.91 → 32: 1.00"（n_q = 24 时 A6 用时是 A4 的 0.91 倍，n_q = 32 时 1.00 倍）。
* **理论估计**：闭式 n_q\* ≈ 4·(链路读回一层复用 K/V 的时间 + GPU 对少量 query 做 attention 的时间) / (PIM 扫一遍 8192 行的时间)，各项取自仿真最小 n_q 点，用来核对仿真趋势，不是结论。
* **验证表**：每个网格点的 A6/A4 时间比（列 = n_q，行 = 模型），<1 表示协同更快。

网格：`results/grid`（n_new ∈ {4…384}，CacheBlend r=0 与 EPIC p=1，两种链路，A4/A6，3 个模型，288 次仿真）。split-K 变体（GPU 对少量 query 的 attention 做 key 切分并行）的结果保留在 `results/turning_points_gridsk*.md`，不在主表中。

# 结论
* NVLink3：协同 prefill 只在 n_q ≲ 23–45（7B → 175B）时更快。换成策略参数：CacheBlend 需要 r ≤ 0.4–0.55 %（默认 15 %，即 1229 行，高出两个量级）；EPIC 同一 prompt 回放时允许的重算 token 总数（p × 段数）≤ 23–36。
* PCIe4：链路读回复用 K/V（每层 0.5–1.6 ms）成为主导，窗口扩大到 n_q ≲ 90–220，对应 CacheBlend r ≤ 1.2–2.7 %、EPIC 重算 token 总数 ≤ 90–214；模型越大窗口越大（每行 K/V 字节随 hidden 增长，PIM 一趟扫描不变）。
* 赢的一侧差额是每请求几 ms（如 175B / EPIC / n_q = 25：NVLink3 下 A4 0.063 s vs A6 0.054 s；PCIe4 下 0.198 vs 0.055 s），只有"对长共享上下文做很多轮短追加"的负载才会累积出来。

# 补充：同一 prompt（没有新 query）的情形，以及复用段长度 L 的影响

如果第二次输入除了位置偏移之外与第一次完全相同（没有新 query），那么 n_q 只剩策略自己重算的行：EPIC 是 p × 段数（默认 1 行），CacheBlend 是 r·L（r = 0.15、L = 8192 时 1229 行）。下表是这种情形（n_new = 1 是格式要求的最小 query，加 1 个 token 的偏移前缀，EPIC p = 1，n_q = 3）以及追加少量新 token 时，复用段长度 L 的影响（LLAMA-7B，flash GPU；单元格 = A4 / A6 的请求 1 prefill 时间 [ms]，括号内 A6/A4）：

| L（复用段长度） | 新 token | n_q | NVLink3 | PCIe4 |
|---:|---:|---:|---|---|
| 2048 | 1（≈无） | 3 | 6.2 / 4.9 (0.78) | 10.0 / 4.9 (0.49) |
| 2048 | 4 | 6 | 6.2 / 5.2 (0.83) | 10.0 / 5.2 (0.52) |
| 2048 | 16 | 18 | 6.4 / 6.1 (0.95) | 10.1 / 6.1 (0.60) |
| 2048 | 64 | 66 | 7.2 / 9.5 (1.32) | 11.1 / 9.8 (0.88) |
| 8192 | 1（≈无） | 3 | 11.4 / 5.5 (0.48) | 26.4 / 5.5 (0.21) |
| 8192 | 4 | 6 | 11.4 / 6.8 (0.59) | 26.4 / 6.8 (0.26) |
| 8192 | 16 | 18 | 11.5 / 10.0 (0.87) | 26.5 / 10.1 (0.38) |
| 8192 | 64 | 66 | 12.7 / 23.0 (1.81) | 27.8 / 23.2 (0.84) |
| 32768 | 1（≈无） | 3 | 32.0 / 7.9 (0.25) | 92.0 / 7.9 (0.09) |
| 32768 | 4 | 6 | 32.0 / 13.1 (0.41) | 92.0 / 13.2 (0.14) |
| 32768 | 16 | 18 | 32.1 / 25.9 (0.81) | 92.1 / 26.0 (0.28) |
| 32768 | 64 | 66 | 34.8 / 77.1 (2.21) | 94.9 / 77.4 (0.82) |

读法：
* 没有新 query 时 EPIC 的 n_q ≈ p，总在拐点以下，协同 prefill 一定更快，而且**优势随 L 放大**（NVLink3：2k 时 0.78×，32k 时 0.25×）——纯 GPU 要把 L 行 K/V 读回并对它们做 CTA 不足的 skinny attention，两项都 ∝ L；PIM 只扫一趟，也 ∝ L 但便宜 4–10×。CacheBlend 在同样情形下 n_q = r·L，r = 0.15 时仍远在拐点之上。
* **拐点 n_q\* 基本不随 L 变**（三种 L 下都在 20–25 之间），L 只放大拐点两侧的差距；所以前面按 L = 8192 给出的 n_q\* 表可以直接用于其他上下文长度，"允许的 r" 则要按 r\* = n_q\*/L 换算（L 越长 r\* 越小）。
