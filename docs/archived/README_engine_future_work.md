## 0. 目标(用户 2026-08-31 提出)

> **64 核 / 200 GB / 几小时**跑完全部 sweep 数据。

换算成硬指标:

| | 现状 | 目标 | 需要 |
|---|---|---|---|
| CPU 时间(80 任务 × 9 档) | **1533 核·小时**(实测模型推算) | 64 核 × 5 h = 320 | **减 4.8×** |
| 单任务峰值内存 | **486 GB**(`GPT-175B × D-hi`) | 200 GB 要装下多个 | **减 20× 以上** |

## 1. 现在的成本结构(实测)

### CPU

全程 py-spy 采样(采满整个 run,不是前缀):

| 阶段 | 占比 |
|---|---|
| decode 构图 `_append_cacheblend_decode_batched` | **83.4%** |
| `validate_cacheblend_events` | 11.3% |
| 调度(已在 C++ 核) | ~1% |
| Ramulator(稳态命中缓存) | ~0% |

热点全部是**对 Python 对象的遍历与临时容器构造**:`sorted()` 排序、
相邻合并成 run、构造地址元组的 set/dict、逐元素展开。**几乎没有浮点运算。**

### 内存(这一项此前被误判过)

| 结构 | 数量(`GPT-175B × D-hi`) | Python 对象 | 列式 int64×2 |
|---|---|---|---|
| **`bindings` 的 KVLocation** | **7000 万** = token × 层 | **19 GB** | **1.0 GB** |
| decode 事件 | 200 万+ × 若干类型 | 大 | 流式后 ≈ 0 |

`GPT-175B × N-hi`(已停放)是 **2 亿个 KVLocation,单这一项 57 GB**。

> **要点:内存的大头是"每 token 每层一个 Python 对象",不是事件图。**
> 一个 `KVLocation` 承载的信息约 16 字节(两个地址 + 几个小整数),
> 却用了约 300 字节存。**先前"流式化即可解决内存"的判断不完整。**

## 2. 三项改动

### F1. `scan_runs` 增量化(风险最低,先做)

**现状**:decode 每一步对整段历史 `sorted()` 再逐个合并成 run,
O(L log L) × 每(输出 token × 层 × 请求)。而每步只在末尾追加一行。

**改法**:维护每 (请求, 层) 的 run 列表,追加时只改末尾。

**难点(必须先证明,不能想当然)**:`scan_runs` 内部按
`(channel_base, channel_count, key_address, value_address)` **排序**,
新追加的行**不保证排到末尾** —— 插到中间会把已有的 run 劈开。
生成的输出 KV 在独立 block 里,地址是否恒在已有 run 之后,**需要在真实数据上
验证**(做法同 `token_offset` 的 rows 不变量检查:包装函数、跑真实 run、
逐次比对增量结果与全量重算结果)。

**估计收益**:1.4×(基于 A+D 之前的 profile 里 `scan_runs` 占 23%)。

### F2. AoS → SoA(列式化)——**地基**

**改法**:把 `KVLocation` / `SplitEvent` 从"每个一个 Python 对象"改成
**平行数组**(`key_address` 一个 int64 数组、`value_address` 一个、
`channel_base` 一个……),用下标而不是对象引用互指。

**它同时解决两件事**:

1. **内存 19×**(300 B/条 → 16 B/条),这是达成 200 GB 的**唯一途径**;
2. **它是向量化的前提** —— 排序变 `np.argsort`、run 合并变 `np.diff` + 布尔掩码、
   集合求交变 sort+merge。

**估计收益**:内存 19×(有把握);CPU **3–10×**(**不确定,是本方案最大的
未知数**)。取决于热点里多少比例能真正变成数组操作 —— run 合并的条件分支和
集合求交向量化后未必快那么多。

### F3. 事件流式化(建立在 F2 之上)

**观察**:事件的依赖是**局部的** —— 只指向同请求同层的前驱或上一个 decode 步,
跨度不超过"一个 decode 步 × 层数 × 活跃请求数"(128 agent × 96 层 ≈ 一万多个
事件)。而调度只需要 `avail[device]` 和依赖的结束时间。

**改法**:从"物化整张 DAG 再排程"改成"**边生成边排程,只保留有界窗口**"。
要维护的结构:

| 结构 | 大小 |
|---|---|
| 每资源时间线 `avail[device]` | 几十个 float |
| 依赖结束时间的环形窗口 | ~万级 float |
| 每 (请求, 层) 的增量 KV 布局(只存 run) | 与上下文成正比,但远小于逐 token |
| 累加器(能量、link bytes、逐 tier 指标) | 常数 |

**两遍走**:①只收集需要 Ramulator 计价的 distinct shape(不建图,便宜)→
并行仿真;②时长已知后流式生成 + 排程,窗口外立即丢弃。

> 老流程本来就是两遍("建全图 → 全丢 → 仿真 → 重建"),W1/W2 为省时间改成
> "建一次 + 占位价 + 回填",**顺带丢掉了两遍的内存优势**。流式方案能同时拿到
> 两者:第一遍不物化,第二遍不保留。

**估计收益**:事件侧内存 → ≈0;CPU 收益不大(主要是省掉对象构造)。

## 3. 为什么 v2(构图主体 C++ 化)不该是下一步

`README_cppcore_branch.md` 的路线图把 v2 定为"构图主体下沉 C++"。但:

- **C++ 化只把常数变小,内存复杂度仍是 O(事件数 + token×层)** ——
  486 GB 还是 486 GB,今晚所有的活锁、杀槽、并发受限**一个都不解决**;
- **F2 改的是复杂度的常数因子中最大的那一项(每条记录 300 B → 16 B)**,
  且在 Python 内即可完成,可逐函数替换、每步逐字节验证;
- 真要 C++ 化,也应当**在 F2 之后**——那时数据已是列式,C++ 侧直接接管数组,
  接口简单得多;先 C++ 化再列式化等于做两遍。

## 4. 一个必须裁决的取舍:逐字节等价

列式化会改变浮点归约顺序。例如 `sum(energy)/1000.0` 换成 `np.sum` 后,
求和顺序变化 → **结果不再逐位相同**。

两条路:

- **(a) 保持标量累加顺序**:放弃这部分向量化收益,换取"逐字节等价"这条
  验证纪律可以继续用(今晚的 36/36 就是靠它);
- **(b) 接受一次口径变更**:允许浮点差异,重新建立基线,此后的验证改为
  "在容差内一致 + 关键指标逐位一致"。

**这条必须由用户定。** 在定之前,F2 的原型应按 (a) 做,先看**不改归约顺序**
能拿到多少收益。

## 5. 建议的推进顺序(不要一次性重写)

今晚的教训是:一次改太多,出问题时定位成本极高。

1. **F1**(`scan_runs` 增量化)—— 局部、可逐字节验证、先证明不变量;
2. **F2 原型** —— 只改 `KVLocation` 的存储与最热的三个函数,在**一个小配置**
   上实测内存与速度,**把"3–10×"变成一个确定的数**;
3. 拿到实测数**再决定**要不要全量重写、要不要 F3、要不要走 (b)。

## 6. 可行性判断

| 指标 | 需要 | F1×F2×F3 估计 | 判断 |
|---|---|---|---|
| CPU 4.8× | 4.8× | 1.4 × (3~10) × 1.16 ≈ **5.4–16×** | **够,但不宽裕** —— 若 F2 只拿到 3× 则刚好 |
| 内存 20× | 20× | F2 的 19× + F3 的事件侧 | **够** |

**结论:64 核 / 200 GB / 几小时是可达的,但成败取决于 F2 的向量化收益,
而那个数字目前只有估计、没有实测。第 2 步的原型就是为了消除这个不确定性。**
