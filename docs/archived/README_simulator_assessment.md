## 一、它到底是什么(能力面,读代码得出)

一个 **GPU–PIM 异构系统上、面向共享 KV 的多智能体 LLM 服务的事件级仿真器**。

| 维度 | 实现 |
|---|---|
| **两条引擎** | 解析(封闭式代价模型,快)+ **物理事件 DAG**(展开每请求每层的事件,重叠与排队由排程涌现)|
| **设备种类** | `GPU` / `PIM` / `DIE` / `LINK` / `TLB` / `ADDR` —— 六类资源各自串行排队 |
| **事件词汇** | 20+ 种,细到 `die_score_assembly`、`decode_die_lse_merge`、`di_bitmap_gpu_to_die`、`decode_batch_pim_kv_scan_score_softmax_pv` |
| **KV 布局** | `none` / `private` / `naive` / `naive-mask` / `master-diff` |
| **通道放置** | `single`(head→1 通道)/ `slice`(head 切片轮转)/ `table`(全局 co-read 放置表)|
| **复用策略** | 6 种:`no-reuse` / `cacheblend` / `epic` / `recompute` / `promptcache` / `cachecraft`(+`cachetune`)|
| **decode 注意力** | GPU 或 PIM;prefill 可 GPU / PIM / **逐请求动态选边** |
| **DRAM 时序** | 经改造的 Ramulator2(HBM3-PIM),签名缓存记忆化 |
| **多轮** | `history_len`:每 agent 自己的历史 KV,按 append 序散落存 |

**规模**:相对 AttAcc 上游 `c1540de` 的初始提交,**+15,797 行 Python**(删 190 行),
现有 11,327 行 + C++ 调度核。96 个提交。

## 二、核心价值:一句话

> **它是目前唯一能在事件级回答"多个请求共享同一份 KV 时,PIM 上的放置、
> 批处理与选边如何相互作用"的仿真器。**

拆开说,它的不可替代性来自三个同时成立的条件:

1. **共享是一等公民**。KV 按指纹跨请求复用,一份存储被 N 个 agent 读。
   AttAcc 是单请求固定 shape;通用 LLM 服务模拟器不建模 PIM 的 bank/通道;
   DRAM 模拟器不懂 KV 语义。**三者的交集只有这里有**;
2. **重叠是排出来的,不是假设的**。事件带依赖、每个设备是串行资源,
   makespan 由排程涌现。这正是它与自家解析引擎的分工 —— 后者用公式假设重叠,
   前者用来检验那个假设;
3. **放置的差别可见**。`single` / `slice` / `table` 三种通道放置能在同一负载上
   对比,而放置差异恰恰是"共享 KV 在 PIM 上到底值多少"的核心机制。

**判断**:第 1 条是真正的护城河。第 2、3 条是把第 1 条做成可测量的手段。

## 三、我们的贡献(分层,如实)

| 层 | 归属 | 内容 |
|---|---|---|
| 上游 | AttAcc(ASPLOS'24) | 解析 GPU 模型、Ramulator2 集成、bank PE 结构 |
| **我们(合作者线)** | xinyao_0821 | CacheBlend PIM 仿真:TLB、master/diff 双池、split prefill、**事件 DAG**、批 decode |
| **我们(本线)** | chenyi-822 | MQ 批命令与时序、多轮历史、A1–A6 阶梯、head→HBM 重映射、参数化 sweep、C++ 调度核、通道放置三型、签名缓存 |

除解析 GPU 模型与 Ramulator2 集成外,**其余均为我们所建**。

### 3.1 最硬的一类贡献:对已发表工件的保真度修正

审计台账(`README_manual_audit_findings.md`)记录 **21 条已解决 + 6 条未解决**。
其中若干条是**上游或基线的真实建模缺陷**,而不是我们自己的设计选择:

| # | 缺陷 | 量化影响 |
|---|---|---|
| **R18** | head↔channel 映射不自洽:上游假设"一 head 一 channel",TP8 下 `n_head_per_hbm=1` → 单通道扫全 L、15/16 通道闲置;池化路径按"幻影 head"逐通道复制列样式 | **能耗虚增约 15×**;修正后"此前全部 PIM 侧数字作废,套件重跑" |
| **R6** | naive 布局**无通道冲突模型** —— 每 run 摊满 16 通道理想并行,**乱序访问零代价** | 这正是本文要论证的现象,在原模型里不存在 |
| **R1** | 计算能量摊进 DRAM 列命令间隔 | 结构性混账 |
| **§1** | 半双工 TSV 通路**方向切换零代价** | 补 JEDEC nRTW/nWTRL;实测代价 ≤0.84% |
| **R16** | decode batch=1 埋没全部布局差异 | 修后 wl_tiny A2 1.81→1.51 s |
| **R20/21** | no-reuse 扫描无驻留容量上限,9,372 个"驻留"查询违反 512 B/8 硬限 | 单 trace 3,014 万行,不可行 |

**判断**:这是最容易被外部认可的贡献 —— 对象是公开工件、发现可量化、
而且**修正改变了我们自己的结论**(结果作废重跑),这是最强的诚实性证据。

### 3.2 方法学贡献(本轮新增)

- **逐字节等价的验证纪律**:任何"只应更快、不应改变结果"的改动,
  必须通过 36 个真实 DAG run 的逐值比对,含 9 个约 25 GB 完整事件流的
  sha256(经 FIFO 流式比对,不落盘)。今晚两轮优化都是这样验证的;
- **不变量先证明再优化**:如 `token_offset` 的改法先在 352 个 block /
  116 万行真实数据上验证"升序无重复",再用 `bisect_left` 替换线性扫描。

## 四、可改进之处(按价值排序,均有实测依据)

### P0. 没有对 AttAcc 已发表结果的复现 —— 最大的空白

查遍 `docs/`,**没有任何一处把本仿真器的输出与 AttAcc 论文的数字做过对照**。
现有的交叉验证是"解析引擎 vs DAG 引擎"和"改代码前后逐字节一致" ——
这两者验的是**自洽**,不是**正确**。

**建议**:在单请求、无共享的配置下复现 AttAcc 的公开结果。对得上 → 底层器件
模型完好;对不上的地方 → **那正是 §3.1 的审计发现本身**。一份实验同时给出
验证与核心发现,而且比"对真硬件"现实得多(HBM-PIM 硬件拿不到)。

### P1. 内存是 O(事件数 + token×层),这是当前一切运行故障的根源

实测(`GPT-175B × D-hi`):

| 结构 | 数量 | Python 对象 | 列式 int64×2 |
|---|---|---|---|
| `bindings` 的 KVLocation | 7000 万 = token × 层 | **19 GB** | 1.0 GB |
| decode 事件 | 200 万+ × 若干类型 | 大 | 流式后 ≈0 |

一个 16 字节信息量的记录用了约 300 字节存。整任务峰值 **486 GB**;
`GPT-175B × N-hi` 预测约 1.34 TB,**超过单节点 1008 GB,不可运行**
(实测表现为活锁:领取→撑爆→被杀→因最长优先又被第一个领走)。

**建议**:列式化(AoS→SoA)+ 事件流式化。详见 `README_engine_future_work.md`。
**注意**:C++ 化(原路线图 v2)只改常数,**内存复杂度不变**,不解决这一条。

### P2. 单档 A1 是长杆,而九档被绑在同一个槽里

实测:A1(`no-reuse`)总耗时约为其余档的 **3 倍**(7427 s vs 约 2400 s)。
但一个槽把九档一起启动、**等全部完成才释放**,所以后 2/3 生命周期里
只剩 A1 在跑,其余八份核空转 —— 实测 CPU 利用率 **26–44%**。

**建议**:把 A1 作为独立调度单位。预计有效并发从 3.6/9 提到接近 9/9。

### P3. 签名缓存池的复利式膨胀(设计缺陷,今晚实测暴露)

```
make_ramdir:    cat pool/${model}__*.jsonl > ramdir/signature_cache.jsonl
publish_final:  cp ramdir/signature_cache.jsonl → pool/${model}__<本任务>.jsonl
```

**每个任务把"启动时读进来的全部内容"又发布回池子** → 分片链式增长。
实测:`GPT-13B` 的分片累计 **19,233 MB,去重后 1 MB**(约两万倍)。
后果是每个新任务要 `cat` 上百 GB、填满节点本地盘、`cat` 失败导致 ramdir
残缺、任务在 80 秒内以 "Need to install ramulator" 失败并被反复重排
(`LLAMA3-8B N-hi` 被启动 **25 次**)。

**建议**:只发布**本任务新增**的签名,或改为单一 append-only 文件 + 定期去重。

### P4. 六条未解决的审计条目

`U1` TLB 描述符常数未溯源且重复收费 · `U2` 总能量预算未定量闭合 ·
`U3` 解析引擎 A2 未对齐"KV 远端"裁决 · `U4` DAG 与解析在 A5 语义分叉 ·
`U5` workload 两条待裁决 · `U6` softmax buffer 第二容量上限。

**建议**:发表前要么解决,要么在"已知局限"里显式声明。U1/U2 审稿人必问。

### P5. 编排层的健壮性

今晚的运行暴露:节点异构未被建模(node5/6 的 `/tmp` 只有 216 GB 而其余 1.1 TB)、
被杀的槽泄漏 ramdir、内存闸门的采样周期(3 分钟)长于任务内存的增长速度
(实测 **60 GB/分钟**,两次采样间可涨 180 GB = 节点的 18%)。

**建议**:节点能力(内存/本地盘)进配置;清理做成幂等且避开启动窗口;
内存采样降到 10 秒级(由节点自采样写文件,而非每轮 srun)。

## 五、总评

**核心价值成立**:共享 KV × PIM × 事件级,这个交集目前没有替代品;
而且我们持有除"解析 GPU 模型 + Ramulator2 集成"以外的全部实现。

**最需要补的是验证**(P0)。没有它,这个仿真器只能证明自己自洽,
不能证明自己正确 —— 而 §3.1 的审计发现恰恰需要一个可信的基线来支撑。

**最需要改的是内存模型**(P1)。它不是性能问题,是**能力边界问题**:
最大的配置根本跑不完,而那恰是共享度最高、最能体现贡献的一端。
