## 3. 受损任务：缺哪些档、为什么

**5 档全部死于节点资源耗尽（磁盘满 / OOM），没有一档是引擎缺陷。**
三个根因都已修掉（见 commit `a798e8a`），补跑不会重演：

1. **`/tmp` 太小** — node5/node6 的 `/tmp` 在 `/` 上，只有 49–62G，
   而一个 trace 重的档要 ~128G。已切到 `/localdata`（3–33T），六节点探针 6/6 通过。
2. **缓存池指数膨胀** — 每次 publish 把任务 seed 来的内容重写回去，
   1MB 两小时后变成 193GB，池子共 499GB，压在一个 98% 满的卷上。已关闭 publish。
3. **内存尖峰被 OOM killer 命中** — 放置改用投影内存而非当前内存。

| 任务 | 已完成 | 缺档数 | 缺的档 |
|---|---:|---:|---|
| `LLAMA-7B / pipeline` (k=8) | 6/9 | 3 | A3 A3a A3b |
| `GPT-13B / private` (k=8) | 8/9 | 1 | A6 |
| `LLAMA-65B / private` (k=8) | 8/9 | 1 | A6 |

补跑总工作量**下限**约 **1.2 个工作单位** ≈ 1.3 slot-小时，排在主批之后，避免和关键路径抢资源。

这是下限而不是估计：它按九档等价折算，但 **A1（`no-reuse`）的图最大，
比其余各档慢约 3 倍**，而 0 个受损任务缺的正是 A1。真实代价明显更高。
