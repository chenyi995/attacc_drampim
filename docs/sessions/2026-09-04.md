# 2026-09-04：A3b 的重算是免费的 —— `shadow_reads` 回答了两个问题

本页由**接手的 AI** 记录。标了"用户裁决"的是 chenyi9 当天的决定；其余是实现与实测。

## 1. 起因：k 变大时 ACT 数量怎么变

用户问：**k 增大时，ACT（activation，打开一个 DRAM row 的命令）数量怎么变？**
特别是 `master_rows = sum(...)` 那个式子。

核对下来，答案是 **A3b 上完全不变**。这不是"偏小一点"，是重算在 A3b 上**完全免费**。

### 1.1 三层刻度（先把几何摆出来）

| 单位 | 字节 | token 数 | 来源 |
|---|---:|---:|---|
| 1 token | 4 B | 1 | `_GEN_BYTES_PER_TOKEN`（`src/workload_runner.py:752`）—— `PIM_MAC_AB` 是 all-bank 广播，一个地址同时点名 16 分区 × 4 bank，256 B 的 K 向量摊薄成 4 B 地址 |
| 1 column | 32 B | **8** | 一次 burst |
| 1 row | 1024 B = 32 col | **256** | `_GEN_ROW_BYTES`（`:751`）；`_STRIPE_UNIT_ROWS = 256`（`:667`）就是这么来的 |

**ACT 只在跨 row 边界时增加。** 在 row 内多占 column 只增加 RD/CAS 次数
（tCCD 量级），不增加 ACT（tRC 量级）。

### 1.2 用户给的算例（裁决口径）

4 个 chunk × 256 token，A4b（master/diff 分池，repair 打包进 diff 通道）：

| k | diff token | 字节 | 占 row D0 的 | diff ACT |
|---:|---:|---:|---|---:|
| 8 | 4×8 = 32 | 128 B | col 0..3 | **1** |
| 32 | 4×32 = 128 | 512 B | col 0..15 | **1** |
| 64 | 4×64 = 256 | 1024 B | col 0..31（正好填满）| **1** |
| 65 | 260 | 1040 B | D0 col 0..31 + D1 col 0 | 2 |

**用户是对的：k 从 8 涨到 32（4 倍），diff 从 4 个 column 变成 16 个 column，
还在同一行里，ACT 仍然是 1。** 要到 k=65 才跨行。

一般式 `ACT = chunk 数 + ceil(总 diff token / 256)`。之前口头汇报用 `C=32` 举例，
`ceil(32k/256) = ceil(k/8)` 正好长得像"k 每加 8 多一次 ACT"——那是 32 这个块数凑
出来的巧合，不是规律。已更正。

## 2. Bug：`shadow_reads` 被用来回答两个不同的问题

`_pool_reads`（`src/workload_runner.py:1123`）改动前：

```python
if getattr(tlb, "shadow_reads", True):
    return _physical_reads(locations)      # 把被修行的 master 副本读回来
return list(locations), set()              # 不读
```

`shadow_reads` 本来回答的是 **die 侧的问题**：被修的那一行的**陈旧 master 副本
参不参与打分**（能掩掉，还是必须切断扫描）。A3 与 A3a 的区别就定义在这上面
（`NaiveKVLayout.shadow_reads = False` at `:1528`；`NaiveMaskKVLayout` 覆盖成 `True`）。

但它在这里被用来回答**另一个问题**：那一行的 **DRAM row 激不激活**。
而这个问题对所有档的答案都是"激活"——那一行剩下的 `256−k` 个 token 还要读。

### 2.1 后果链

`kv_mapping="naive"` 走 `NaiveKVLayout`（`:3738`），而 `src/ablation.py:107` 的 **A3**
和 `:118` 的 **A3b** 都是 `kv_mapping="naive"`。于是 A3b 的 `reads` 里**从来没有**
那 `C·k` 个 shadow master 行。接着 `_striped_append_channel_extents` 的

```python
master_rows = sum(rows for kind, rows in extents if kind != "diff")   # :822
```

只数到活下来的，`_stream_unit_rows`（`:672`）再把剩下的**连续重新打包**——
洞不是"不激活"，是**被合上了，流真的变短了**。

减掉的（master）和加上的（repair）逐 token 抵消，**总量恒为「可见 token / 256」，
与 k 无关**。

### 2.2 具体例子：4 chunk × 256 token，A3b，k=64

**应有**（owner 的 4 行照开，head 自己的 repair 是一段连续 append）：

```
row M0  col 0..31   chunk0 —— 读其中 192 个,跳过散落的 64 个;
                    跳过的还在这一行里,行照样要开        ← ACT
row M1  col 0..31   chunk1                               ← ACT
row M2  col 0..31   chunk2                               ← ACT
row M3  col 0..31   chunk3                               ← ACT
row R0  col 0..31   本 head 的 4×64 = 256 个 repair      ← ACT
                                                       总计 5
```

**改动前模型算出来的**（先减掉 256 个 token，再把剩下 768 个连续打包）：

```
master_rows = 1024 - 256 = 768  →  units = [256, 256, 256]
row M0' col 0..31   ← ACT
row M1' col 0..31   ← ACT
row M2' col 0..31   ← ACT        ← 第四行凭空消失
row R0  col 0..31   ← ACT
                   总计 4
```

owner 是在 consumer 出现之前就 append 完的，**consumer 压不动它**。

### 2.3 方向：折扣落在本该输的那一档

A4/A4b/A5/A6 走 `CacheBlendTLB`（`shadow_reads=True`），shadow 行原样读回来，
`master_rows` 恒为可见 token 数，**与 k 无关，正确**。
只有 A3b 拿到这个折扣——而 A3b 正是 master/diff 分池要打败的那一档。
所以模型里 **A3b 比 A4b 便宜，且 k 越大差距越大**，池的收益不只是看不见，是符号反了。

## 3. 用户裁决（2026-09-04）

1. **动手修**。
2. 修在 `_pool_reads`：`shadow_reads` 只管掩码，不管激活。
3. 保留 A3/A3a 的区分（见 §4.2 的门）。

## 4. 改了什么

### 4.1 `src/workload_runner.py:1123` `_pool_reads`

```python
if (getattr(tlb, "shadow_reads", True)
        or getattr(tlb, "layout_policy", None) in _APPEND_POLICIES):
    return _physical_reads(locations)
return list(locations), set()
```

**只改了这一个条件**，`:822` 的 `sum` 一字未动——那个式子算的是"physically
streamed 的 master token 数"，定义本身没错，错的是喂给它的 `reads` 缺了行。
在 `:822` 里补要从 `location.shadow` 反推，而 A4b 的 shadow 已经在 `reads` 里了，
会重复计数；补在唯一入口没有这个问题。

### 4.2 那个门：`layout_policy in _APPEND_POLICIES`

`layout_policy` 每个 TLB 都有（`CacheBlendTLB.__init__` `:1199`；
`NoReuseKVLayout` 是类属性 `:1367`）。实测取值：

| 档 | kv_mapping / placement | layout_policy | 属于 `_APPEND_POLICIES` | 本次是否改变 |
|---|---|---|---|---|
| A1 | private / slice | `slice` | 否 | 否 |
| A3 | naive / single | `single` | 否 | 否 |
| A3a | naive-mask / single | `single` | 否 | 否 |
| **A3b** | naive / slice | `slice-append` | **是** | **是** |
| A4 / A4b / A5 / A6 | master-diff / slice、table | `master-diff-*-append` | 是 | 否（本来就 `shadow_reads=True`）|

**这个门精确地只打开 A3b。**

不加门（总是展开）的话 A3 也会跟着变——实测 A3 的最忙通道载荷从 8192 变成 8448，
**与 A3a 逐字节相同**，这一档的对比就没了。`masked_rows` 只进报告、不进时间和能量
（`:1683-1693` 的 `time_s`/`energy` 全部来自 Ramulator 的 `measured`，`:2175` 只做
上界校验），所以去掉门之后两档不会有任何数值差异。用户裁决保留区分。

### 4.3 一个顺带确定的口径：A3b 现在会记 `masked_rows`

改动后 A3b 的 `reads` 里有了陈旧 master 行，`_physical_reads` 同时把它们放进
`masked` 集合。**这是对的**：`masked_rows` 的含义是"DRAM 流过、但打分忽略"，
A3b 正是如此——行为了别的 token 被打开，陈旧那个不进打分。
写单测时先按"A3b 无掩码门 → `masked` 应为空"断言，测试失败，据此改正口径。
`masked_rows` 是报告字段，不影响时间与能量。

- **一条未验证的前提**：上面 column 级几何假设 Ramulator 那一侧也按 4 B/token 记

## 9. 上午那次修正做对了一半，另一半是错的

**做对的**：被跳过的 master 行必须进 `reads`，因为那一行照样要开（4 B/token，一行 256 token）。
能量 +0.75%、带修正扫描的 ACT +8.6%，方向正确。

**做错的**：`_pool_reads` 返回的**同一个列表**被三处使用，它们要的东西不同：

| 用途 | 需要什么 | 上午的改动做了什么 |
|---|---|---|
| `_append_placement_pim_scan(reads=…)` → extent / ACT | shadow 行**要在**（行照开）| ✅ 对 |
| `tlb.scan_runs(reads)` → TLB 描述符 | 无掩码门时 run **必须切断** | ❌ 空洞被填上，run 合并 |
| `masked` 集合 | A3b **不能掩码** | ❌ 给它记了 `masked_rows` |

`NaiveKVLayout` 的定义就是 "a corrected row's master copy is **skipped, splitting the master
run**"。上午的改动让 run 不再切断 —— 那是 **A3a** 的性质，等于把 A3a 的能力给了 A3b。

实测这一处的量级（一个 256-token 块、8 个散落修正位置，用真实的 t1n0 位置）：

```
改前  locations=256  scan_runs=10   TLB plan = 5.0e-8 s
改后  locations=264  scan_runs= 2   TLB plan = 1.0e-8 s
```

**A3b 变快的 5.48% 里，93% 来自这里**（见 §10）。

### 10.1 阶梯在掩码门上不是单调的

| 档 | kv_mapping | TLB 类 | `shadow_reads` |
|---|---|---|---|
| A3 | naive | `NaiveKVLayout` | **False** |
| A3a | naive-mask | `NaiveMaskKVLayout` | **True** |
| **A3b** | naive | `NaiveKVLayout` | **False**（**退回**）|
| A4 / A4b / A5 / A6 | master-diff | `CacheBlendTLB` | **True**（**又加回**）|

A3（无掩码）→ A3a（加掩码）→ A3b（**退回**无掩码 + head 切片）→ A4（**又加回**掩码 + 分池）。

**所以 A3b→A4 这一步同时动了两个变量**：分池（预期）+ 掩码门（夹带）。夹带那个的效应
0.83 s，**比 A3b–A4b 的全部差距 0.286 s 还大**。

`--pipeopt` 下 TLB 事件会拿到自己的资源时间轴（`_schedule_cacheblend`：
`resource = event.device if pipe else "SERIAL"`），跨请求可重叠；但它是自己那次扫描的依赖，
链内仍串行。**本轮与 colpack 都没开 `--pipeopt`**（两个脚本里出现 0 次），所以 0.84 s 全额计入。
能藏掉多少**未实测**。

## 11. 四处「求和/排序坍缩」（chenyi9 2026-09-04 晚指出）

用户的质疑：A4/A4b 有明确的收益来源（多个 head 的 repair 集中到一行），
为什么实测反而倒挂？逐层查下来，是模型把收益抹掉了。

取一次真实的 t1n0 decode 扫描（layer 0，`heads_per_hbm=8`）：

```
_read_extents 切出 43 段：master 19 段（2708 token）+ diff 24 段（136 token），交错排列
  master 256 | master 20 | diff 1 | master 112 | diff 1 | master 23 | diff 1 | ...
模型实际放置：每 head 6 个 slot（[256]×5 + 尾巴），共 96 个 slot、96 次 ACT
```

| 计价方式 | 总 ACT | master | diff |
|---|---:|---:|---:|
| **模型现状**（两侧各求和后重新打包）| **96** | — | 两档都算 1 段 |
| 按真实段 · **A3b**（修正就地）| **344** | 152 | **192** |
| 按真实段 · **A4b**（修正进池）| **157** | 152 | **5** |

**池在 diff 侧本该省 192→5，模型对两档都只算 1 段。**

### 11.1 四处，按严重程度

| # | 位置 | 坍缩掉什么 |
|---|---|---|
| 1 | `:822` `master_rows = sum(...)` | master 段结构。上午修了**入口**（shadow 行加回 reads），**坍缩本身未修** |
| 2 | `:823` / `:870` `sum(repairs)` | diff 段结构 —— **正是分池的收益** |
| 3 | `_stream_unit_rows`（`:672`）跨 owner 重新打包 | 不同 owner 是独立分配，压不到一起 |
| 4 | **`CacheBlendTLB.finalize`（`:1263`）的 `sorted()`** | **写入时序** |

### 11.2 第 4 条：A4–A6 拿到了物理上不可能的布局

| 类 | 服务的档 | 分配顺序 | 行号 |
|---|---|---|---|
| `NaiveKVLayout` | A3 / A3b | `enumerate(self._reserved_rows)` —— dict 插入序，注释写明是 **"software append order"** | `:1573` |
| `CacheBlendTLB` | **A4 / A4b / A5 / A6** | `enumerate(**sorted**(self._reserved_rows))` | `:1263` |
| `NoReuseKVLayout` | A1 | `enumerate(sorted(self._reserved))` | `:1416` |

**`sorted()` 就是完美预知。** 它按 `(layer, owner, fingerprint, kind)` 排序分配，于是同一个
owner 的块天然连续、**跨 agent 的并发写入交错完全不存在**。而 A3b 走真实 append 序，
别的 agent 的页就夹在中间。

用户的原话：*「diff channel 的 diff 侧也不能预知未来提前拿到 Q」*。正是如此 ——
**A3b→A4 这一步还偷偷把「append 序」换成了「全知排序」**，这是第二个夹带的变量。

### 11.3 池的真实收益量级（推导，未实测）

k=8 时一行 1024 B = 256 token = **32 个 repair**。若 W 个 agent 并发写入池，
消费者要的 repair 与另外 W−1 份夹在一起，每碰一行只有 1/W 有用 ——
**池的收益从 32× 退化到约 32/W×**。本 workload `--cacheblend-batch-size 8`、
tier-1 有 16 个 agent，W 在 8 量级，收益约 **4×**，不是 §11 表里那个 38×。

**这是推导，没有实测**，因为模型里根本没有交错这回事（第 4 条）。

## 12. 被这些坍缩影响的、必须撤回的结论

| 「§16 裁决把池的收益砍到只剩 4 次 ACT」 | **说反了** —— §16 说的是「一个 head **一轮**自己的 repair 连续」，被我错误推广成「整个扫描的 repair 是一段」。跨轮、跨 agent 的部分复用会切碎它 |

仍然成立的：
- A4 在 `--num-hbm 1` 上 `stripe_m = 15//8 = 1` 的退化（纯取整，与 extent 无关），
  引擎自己报 `placement_degeneracy_warning`；
- 地址刻度：Ramulator 侧 4 B/token（`MAC_AB` 广播 16 分区，`score_mac` 每 16 token 走
  2 个 32 B column），1 row = 1024 B = 256 token，与 `_GEN_*` 常数逐个对上（**已验证**）；

  另合成一套，`pim_kv_extent_groups` 覆盖），两把尺子不可比。

## 13. `shifted` 判定漏了前置上下文变化（chenyi9 2026-09-04 指出）

## 15. 修改计划

按依赖顺序分四步，每步单独可验证、单独提交。**每一步都会改变已发布的数**，
所以每步都要重跑并在文档里标明作废范围。

### P0：拆开 `_pool_reads` 的三个用途（撤销 09b50fb 的附带损害）

`_pool_reads` 现在返回一个列表供三处使用，而它们要的东西不同（§9）。改成分别供给：

- **放置 / extent / ACT**：用 shadow 展开后的列表 —— 行照开，重算是增量（09b50fb 的正确部分，保留）；
- **`tlb.scan_runs` / TLB 描述符**：无掩码门时用**未展开**的列表 —— run 照切断，恢复 A3b 的定义；
- **`masked` 集合**：`shadow_reads=False` 时保持为空 —— A3b 不能掩码。

影响：A3b 的 TLB 时间回到 0.84 s 量级；A3b 的 makespan 应回到 16.4554 附近
（`KVPIM_LEGACY_POOL_READS=1` 的对照跑正是为验这一条）。A4–A6 不受影响。

### P1：分配顺序改 append 序（用户裁决 + 2026-09-04 晚的补充口径）

**补充裁决**：prefill 与 decode 要分开看。

- **prefill 可以一起做**：各 agent 的 sys 是同时拿到的，prefill 是一批完成的，
  所以每个 request 的 prefill 块（master / diff / history）**连着落盘是合理的**，
  这一段不是分歧的来源。
- **decode 才是分歧的根源**：有的 agent 少生成一个 chunk、有的多生成两个；
  而且**每个 agent 的 sys 长度也不一样，扫到 shared chunk 的时刻不同**。
  所以 decode 生成的行在 append 流里**必然跨 agent 交错**。

现状（`_prepare_cacheblend_tlb`，`:2542-2565`）两处都不对：

```python
for layer in range(ndec):
    for request in workload.requests:
        _reserve_cacheblend_tlb_rows(...)          # prefill 的 master/diff —— 这样是对的
        history 块
        for output_row in range(request.lout):     # decode 行 —— 一个 request 的 lout 个
            tlb.reserve(..., output_row, "master") #   连着预留完，再轮到下一个 request
```

**P1a**：`CacheBlendTLB.finalize`（`:1263`）与 `NoReuseKVLayout.finalize`（`:1416`）
去掉 `sorted(...)`，改用插入序，与 `NaiveKVLayout:1573` 一致。
不去掉的话下面 P1b 做什么都会被重新排序抹掉。

**P1b**：把 decode 输出行的预留改成**按生成步跨 request 交错**：

```python
# prefill / history：保持按 request 成组（一批 prefill，同时完成）
# decode：按步交错，lout 短的 agent 自然在后面的步里退出
for step in range(max(r.lout for r in requests)):
    for request in requests:
        if step < request.lout:
            tlb.reserve(layer, request.request_id, output_fp, step, "master")
```

这样「A 少一个 chunk、B 多两个」直接体现在流里：先结束的 agent 从后续步中消失。

**未建模、需另行裁决**：sys 长度不同导致各 agent **进入 decode 的时刻**不同，
严格说应按预计完成时间排序，而不是按 request 顺序。但布局在仿真之前就要定，
时序又依赖布局 —— 鸡生蛋。P1b 用「按步交错、步内按 request 顺序」作为一阶近似，
**这是近似，不是实测口径**。

影响：**七档全部要重跑**（P1a 动 A1/A4–A6，P1b 动所有档）。

### P2：extent 忠实化（第 1、2、3 条坍缩）

`_striped_append_channel_extents`：不再 `sum` 后用 `_stream_unit_rows` 重切，而是
**逐段**送进 `_channel_extent_addresses`：

- master：`units = [u for e in master_extents for u in _stream_unit_rows(e)]` ——
  保留 stripe 轮转规则，但**每段单独切**，不跨段打包（同时解决第 1 和第 3 条）；
- diff：`add(...)` 逐段，而不是 `sum(repairs)` 一段（第 2 条）。

**先决条件**：`_physical_reads`（`:1130`）把 shadow 行插在 diff 行**旁边**，不是它在 owner
chunk 里自己的位置，`_read_extents` 按列表相邻分组会因此炸出 2k 段（实测 C=4、k=32 时
8 段变 256 段）。P2 之前必须先修这个插入位置。

影响：**A3b–A6 五档全部重跑**，ACT 会大幅上升（上面那次扫描 96 → 157/344 量级）。

### P3（需要另一次裁决，本次不做）：两套地址模型合一

`_channel_extent_addresses` 合成的地址与 TLB 的真实地址是两套（§12），
`pim_kv_extent_groups` 覆盖掉后者。真正的物理邻接由 TLB 分配决定，所以 extent 的
唯一真相应该是 `tlb.scan_runs(reads)`，而不是另一套合成。合并这两者需要把放置策略
（slice / table / master-diff）表达进 TLB 的分配里，是一次大重构 —— **本次不做，记在这里**。
