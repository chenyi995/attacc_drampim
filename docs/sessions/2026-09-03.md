# 2026-09-03：A3b–A6 换成 striped-append 布局 + 本机（无 Slurm）跑通

本页由**接手的 AI** 记录。标了"用户裁决"的是 chenyi9 当天的决定；
其余是实现与实测。

## 1. 起因：A3b 的两层模型互相矛盾

用户先问 A3/A3a 上是不是总有 channel 空着。核对代码后确认：

- **A3/A3a（`single`）的活跃 channel 数恰好 = `heads_per_hbm`**，其余空着。
  `ablation.py` 对 A3 的原注释就是 "the worst-case naive floor; other channels
  idle"。baseline 配置下 LLAMA3-8B 空 8 条、GPT-13B 空 14 条、LLAMA-33B 空 13
  条、**LLAMA-65B 与 GPT-175B 16 条只用 1 条**；LLAMA-7B（32 head）不空。
- **A1 不空**：`_layout_policy` 把 `private` 映射成 `slice`，`heads × stripe
  = heads × (16 // heads)`，整除就铺满。空 channel 数 = `16 mod heads`
  （`heads ≤ 16` 时），所以只有 LLAMA-33B（heads=3）空 ch15 一条。
- 附带发现：`slice` 在 **heads ≥ 9** 时 `stripe` 就钳到 1、与 `single` 逐位相同，
  不是 docstring 暗示的"挤满 16 条"。

再往下核对 A3b，发现**地址分配器与时序模型说的是两回事**：

| | c、d（各 8 token 的 diff）落在哪 | e（256 token）接着放哪 |
|---|---|---|
| `NaiveKVLayout.finalize`（地址）| **不同** channel，各占 2 KiB = 2 个 DRAM row | 再下一条 channel（`rotation % 16` 全局轮转）|
| `_placement_channel_runs`（时序，出 makespan）| **合并成一个 chunk**，同一条 channel，按 **256 行**计价（真实 16 行）| 按 chunk 计数轮转 |

而 `_append_placement_pim_scan` 里 `scan_op.pim_kv_runs = runs` 直接**覆盖**掉
`tlb.scan_runs(reads)` 的真实地址，所以分配器那套地址只喂 `_tlb_plan_cost` 和
report，**跟 makespan 无关**。行级效应（跨行、共享行、mid-row 起步）一个都没进模型。

## 2. 用户裁决（2026-09-03）

1. **A3/A3a 不动**，A1 不动 —— 保留"一 head 一 channel"的朴素下界与 AttAcc 参照点。
2. **A3b 及之后（A3b/A4/A4b/A5/A6）全换成 striped-append 的真实行数模型。**
3. `heads_per_hbm > 16`（LLAMA-7B 的 32）时多个 head 共用一条 channel，**交织成一条流**。
4. 布局形状由用户给定的例子定义（下节）。

## 3. striped-append 布局

一个 head 的 KV 是**一条连续的 append 流**，切成 256-token stripe unit，
unit `u` → 该 head 的 channel `base + (u % stripe)`；channel 内**打包**：
短段不补齐到 256，填满当前 unit 就续到下一条 channel。

用户给的例子（head 占 ch0..ch3，依次 append a=256 b=256 c=8 d=8 e=256 f=256）：

```
a -> ch0 unit0 row 0..63        d -> ch2 unit0 row 2..3
b -> ch1 unit0 row 0..63        e -> ch2 unit0 row 4..63 -> ch3 unit0 row 0..3
c -> ch2 unit0 row 0..1         f -> ch3 unit0 row 4..63 -> ch0 unit1 row 64..67
每 channel 行数：ch0=272, ch1=256, ch2=256, ch3=256
```

实现：`src/workload_runner.py`
- 新增 `_STRIPE_UNIT_ROWS`、`_APPEND_POLICIES`、`_stream_unit_rows()`、
  `_striped_append_channel_rows()`。
- `_layout_policy` 新增三个 policy 名，**A1/A3/A3a 的映射一字未动**：

  | rung | kv_mapping / channel_placement | policy | 模型 |
  |---|---|---|---|
  | A1 | private / slice | `slice` | 旧 chunk 计数 |
  | A3 / A3a | naive(-mask) / single | `single` | 旧 chunk 计数 |
  | A3b | naive / slice | **`slice-append`** | 真实行数 |
  | A4 | master-diff / slice | **`master-diff-slice-append`** | 真实行数 |
  | A4b/A5/A6 | master-diff / table | **`master-diff-table-append`** | 真实行数 |

  A3b 必须另起名字，因为 `private` 和 `naive+slice` 原本**都**映射成 `slice`，
  直接改 `slice` 会把 A1 一起改掉。
- `_placement_channel_runs` 按 policy 分派；`loads` 统一成**行**单位（旧分支乘
  256），旧分支的 run 行数逐位不变。
- `placement_degeneracy_warning` 的文案改了：A3b 不再与 A3 逐位相同（padding 口径
  不同），但 channel 分布仍是同样的一 head 一 channel 堆叠，警告依然成立。

## 4. 这个改动值多少

**在 baseline（C=32、k=8）参数上是数值 no-op** —— 8192 和 256 都正好是 256 的
整数倍，没有 padding 可去，六个模型的 A3b/A4/A4b 最忙 channel 行数改前改后完全相同。
有效果的是长度不整除 256 的配置：

| reads（master+diff）| A3b old→new (h=8) | A4b old→new (h=2) |
|---|---|---|
| C=32 k=8  8192 | 4096→4096 (0%) | 1280→1280 (0%) |
| C=32 k=2  8192 | 4352→**4096** (−5.9%) | 1280→1280 (0%) |
| C=16 k=8  4096 | 2304→**2048** (−11.1%) | 768→**640** (−16.7%) |
| +16 sys token 8208 | 4352→**4112** (−5.5%) | 1280→1280 (0%) |

k=2 时 A4b 的 diff channel（ch15）从 512 行降到 128 行，4 倍虚高被去掉；只是 ch15
在 baseline 上不是最忙的那条，所以不改 makespan。

## 6. 本机（无 Slurm）跑不起来 —— 两个独立的坑，都已解决/定位

### 6.1 `KVPIM_CPPCORE=1` 段错误 → **是 .so 陈旧 + Makefile 用错编译器（已修）**

现象：`terminate called after throwing an instance of 'std::length_error'
what(): vector::_M_range_insert`，`tests/test_workload.py` 和任何 dag run 都崩。
**在原始代码上同样复现**，不是布局改动引入的。

根因：`src/cppcore/Makefile` 写的是

```make
CXX ?= /opt/rh/gcc-toolset-11/root/usr/bin/g++
```

**`?=` 对 `CXX` 永远不生效** —— GNU make 内置就定义了 `CXX = g++`，`?=` 只在变量
未定义时赋值。所以 `make` 一直在用系统编译器（本机 gcc **8.5.0**），而注释里写的
build convention 是 gcc-toolset-11。仓库里带的 `libeventcore.so` 是 8-29 编的，
和当前源码/工具链对不上。

修法（已提交到工作区）：`?=` 改成 `=` 并加注释说明原因；命令行
`make CXX=...` 仍然可以覆盖。重编后：

```bash
cd src/cppcore && make      # 现在真的走 /opt/rh/gcc-toolset-11/root/usr/bin/g++
```

**验证**：A1 / wl_tiny / CACHEBLEND-TINY 在 `KVPIM_CPPCORE=1` 下 rc=0，
makespan `0.059978271549260116`，与 `KVPIM_CPPCORE=0` **逐位相同** ——
C++ 核与 Python 核互相印证。

本机可用的工具链：`/opt/rh/gcc-toolset-{9,11,14}`，系统 gcc 8.5.0，Python 3.10.13。

### 6.2 tiny 模型上 `rows=0` 的校验失败 —— **已定位，未改**

现象：A3b/A4 在 `wl_tiny` + `CACHEBLEND-TINY` 上退出码 2、**日志里看不到原因**。
`main.py:588` 把 `WorkloadValidationError` 交给 `parser.error(str(exc))`，
argparse 于是 `sys.exit(2)`，把一个真实的建模错误伪装成命令行错误。

真正的异常：

```
src.workload.WorkloadValidationError: CacheBlend event has an invalid shape or cost
  workload_runner.py:1974  validate_cacheblend_events   (event.rows <= 0)
```

44952 个事件里 224 个 `decode_pim_kv_scan_score_softmax_pv` 的 `rows=0`，
集中在编号大的 pool（pool2/4/…/14）。成因：`_append_placement_pim_scan` 为了出
report，把**一个 head 的** `reads` 轮转分给**所有活跃 channel**；当
`len(reads) < len(active)` 时尾部 channel 分到 0 行。

- **原始代码同样触发**（隔离目录 A/B 验证过），不是本次改动引入的。
- 只在上下文短于活跃 channel 数时出现，**baseline sweep（C=32，8192 行）不会触发**，
  所以集群上那 54 个点没受影响。
- `event.rows` 在 PIM 扫描事件上**只被校验器读**（`workload_runner.py` 的 348 /
  1973–2005 / 3444），不参与任何计价。
- **没有改**：修它要改 report 里 `rows` 的口径（改成该 channel run 的行数，或
  保证每条活跃 channel 至少 1 行），会动到已发布报告的字段语义，等 chenyi9 裁决。

## 8. heads-per-HBM 修正（用户 2026-09-03 当天发现并裁决）

用户问："GPT-175B 一共 96 个 head，为什么平均每个 HBM 才一个 head？应该是
96/40，最多的 HBM 是三个 head。"

**用户是对的，而且不只是"记载不符"。** `_heads_per_hbm(kv_heads_local, num_hbm)`
把 KV head 按张量并行切了（`kv_heads_local` 已经是 `num_heads // tp`），
**却没有把堆栈也切** —— 每个 GPU 拿到全部 `--num-hbm` 个堆栈。全仓库 30 处
`num_hbm` 里没有任何一处除以 `ngpu`/`tp`；六个调用点全部直接传
`accelerator.num_hbm`。后果不是"数不一样"，是一台说不通的机器：

| 模型 | 修前 heads/HBM | `num_hbm_used` | 修后 |
|---|---:|---|---:|
| LLAMA-7B | 32 | 1 / 1 | 32（不变，ngpu=1）|
| LLAMA3-8B | 8 | 1 / 1 | 8（不变，ngpu=1）|
| GPT-13B | 2 | 10 / 10 | **4** |
| LLAMA-33B | 3 | 9 / 10 | **6** |
| LLAMA-65B | 1 | **8 / 40（32 个闲置）** | **2** |
| GPT-175B | 1 | **12 / 40（28 个闲置）** | **3** |

没人会配 40 个堆栈只用 12 个。`experiments/run_sweep_models.sh` 抬头注释与
`docs/README_baseline_postfix_results.md` §5 写的 32/8/4/~5/2/3 记的正是正确意图 ——
**是代码没实现文档，不是文档记错**；此前本页把责任归反了，已更正。

### 用户裁决的修法（"第一种方法，注意要向上取整，只需要仿真一个最忙的 HBM"）

新增 `_hbm_stacks_local(num_hbm, tensor_parallel)` = `num_hbm // tp`（**向下取整**：
一个 GPU 不可能拿到比机器更多的堆栈，除不尽时剩下的零头也不会让任何 GPU 的最忙堆栈
变轻）；`_heads_per_hbm` 增加第三个参数 `tensor_parallel`，改成
`ceil(kv_heads_local / _hbm_stacks_local(...))`。**向上取整**是有意的：扫描时间由最忙的
那个堆栈决定，所以只需要仿真最忙的那个 —— 96 个 head 摊 40 个堆栈，有的 3 个有的 2 个，
模型按 3 计价。

在六个 sweep 配置上，"按 GPU 切" 与 "全局 `ceil(KV head 总数 / num_hbm)`" 完全等价
（`ngpu` 整除 `num_hbm`），单测两条都钉住了。

改到的地方：`_heads_per_hbm` 与新的 `_hbm_stacks_local`；五个
`_append_placement_pim_scan` 调用点 + A6 探针，全部补传 `system.model.tp`；
`placement_degeneracy_warning` 的调用与它自己的 `kv_heads_total` 重建
（原来写 `heads_per_hbm * num_hbm`，同样漏了 tp）；`main.py` 的 `--num-hbm` 帮助文本
（含义从 "per accelerator" 变成"整个系统的堆栈数"）。

单测：`tests/test_placement.py` **40 个全过**，新增 6 个 `HeadsPerHBMTest`
（六个 sweep 配置逐个对上意图、与全局比值等价、堆栈按 GPU 向下取整、
向上取整到最忙堆栈、GPT-175B 不再闲置堆栈、单 GPU 模型不受影响）。
`tests/test_workload.py` 41 个全过。退化警告仍只对 LLAMA-7B 触发，正确。

### 影响

`single`（A3/A3a）的最忙 channel 载荷 = 一个 head 的全部 chunk，与堆栈上挤了几个 head
无关（head 数 ≤ 16 时），**A3/A3a 不受影响**；`slice` 系（A1、A3b，stripe = `16 // heads`）
与 master-diff 系（A4/A4b/A5/A6，`stripe_m = 15 // heads`）直接随它变，
**四个多 GPU 模型的这六档全部要重跑**。`fig/plots/exp1/` 里那批数是修正前跑的。

## 9. 顺带查出、**未修**：`num_attacc` 恒为 8，与 `--ngpu` 无关

`main.py:528` 调 `make_pim_config` 时不传 `num_attacc`，用的是
`src/config.py:265` 的默认值 **8**；没有对应的命令行开关。而 PIM 能量在
`devices.py:483` 与 `:526` 都乘了 `self.num_attacc`（时间没乘，正确 —— 各加速器并行）。

一次扫描事件代表**一个 GPU** 那份 head（`op.numOp = _gqa_kv_heads_local(...)`），
乘 `num_attacc` 是为了补上其余 GPU 的加速器。所以只有 `--ngpu 8` 时对得上：

| `--ngpu` | 模型 | PIM 能量倍率 |
|---:|---|---|
| 8 | LLAMA-65B、GPT-175B | 正确 |
| 2 | GPT-13B、LLAMA-33B | **4× 偏大** |
| 1 | LLAMA-7B、LLAMA3-8B | **8× 偏大** |

GPU 侧没有这个问题（`system.py:252` 按 `num_xpu` 缩放，与 `--ngpu` 一致），
所以受影响的是 **PIM 与 GPU 的能量之比**，以及跨模型的能量/功率可比性 ——
`fig/plots/exp1/` 那张功率表里六个模型不同倍率，不能横向比。

**没有改**：`num_attacc` 该不该跟着 `--ngpu` 走，是建模语义，等 chenyi9 裁决。
若要改，`make_pim_config(num_attacc=args.ngpu)` 一行即可，但会动到
`aggregate_memory_capacity`（`= 16 GiB × num_attacc × num_hbm`）的口径。
