## 2. magic-number 核查：47/49 其实有依据（我先前判断有误）

**问题**：为什么 star=47 chunk、debate=49 chunk（非整、非 cap 分数）？

**核查过程 → 结论**：`chunks = ceil(shared_tokens/256)`，所以 47=12032/256。
一开始只看 codebase 那一段（占 cap 37%）判它"无依据"——**错了**。查**最大单段
= agent 的 history extent**：star 27,764 / pipeline 28,336 / debate 28,304，
**全部 85–86% of the 32,768-token cap**。即 12032/12544/12800 是"把最深
history extent 填到 cap 的 85–86%"反推出来的，三个数不同是因为三种编排的
每轮累加结构不同——**这才是真依据**（文档那条"顶到上界 76–86%"）。

**cap 溯源**（`cap × 76%` 的出处）：
- **8-MiB K 窗**是 AttAcc 原始物理布局（`src/workload_runner.py:735-737`：
  "the 8-MiB K window is full → next 16-MiB channel tile"；`src/ablation.py:61`），
  32,768 = 8 MiB ÷ (d_head×2 B = 256 B/token)——硬依据；
- **"76%"无外部出处**，是自定 margin（`docs/README_run_experiments.md:27-28`
  "顶到上界 76–86%，合理范围内尽量大"），RAG 的 96 恰落 76% 是**结果**不是推导。

## 3. 一次失败的"统一到整数"尝试（已撤销）

先试把多轮语料统一 64 block（16384）+ message 全 256——**撑破 cap**：新 history
extent 冲到 107–112%，引擎会拒。根本矛盾：**"填满 cap 到 85%"要 workload-specific
非整 corpus；"取整 corpus"要么撑破 cap、要么浪费**。已 `git checkout` 撤销脚本改动、
删掉坏的 k64 workload。

## 4. 裁决（chenyi9）：改用参数化 sweep，结构性消除 magic number

把 workload 建成**分层 DAG（tiered DAG）**：4 种 node（in/out 尺寸 2×2）、tier
宽度可变、fan 由 in/out 尺寸隐含（fan-out 1→N / fan-in N→1 / all-to-all / pipeline）；
扫 **(N, C, D, k)**。**history 改按 append 序散落建模**（多段、不吃单段 cap），
所以 C ≤ 64 block ≤ 50% cap 即可，**全整数、零 magic number**。设计文档
`docs/README_sweep_design.md`（含 §7"每个 sweep 轴凸显哪对 A 档区别"，结合归档结果佐证）。

**落地**：
- `workload/gen_sweep.py`：一个脚本，`--topology {broadcast,reduce,alltoall,
  supervisor,pipeline} --N --C --D [--private]`；k 是 run 时参数（EPIC_K）；
- `workload/sweep/*.json`：12 个 distinct workload，全 ≤50% cap，agent 4–128；
- `experiments/run_sweep.sh` / `run_sweep_parallel.sh`：14 config × 7 档 = **98 run**；
- topology 术语用 CS 词（fan-out/fan-in/all-to-all/pipeline/supervisor/reduce）。

**sweep 值**（chenyi9 定）：N{4,16,64}、C{16,32,64}、D{1,2,4}、k{2,8,32}，
baseline (alltoall,16,32,2,8)；OFAT + 4 topology 变体 + 1 private 对照。

## 7. head-aware channel placement 重切阶梯（chenyi9，当天晚些）

**裁决**：一个 head 的一个 chunk = 一条 channel 的一个 row；decode 扫描时间 =
**最忙 channel**（一起读、落同一条 channel 的 chunk 串行）。head 间 HBM 并行，
`heads_per_hbm = ceil(局部 KV head / num_hbm)` 个 head 共享一个 HBM 的 16 条 channel。

**阶梯扩到 9 档**（`src/ablation.py` PRESETS + `channel_placement` 字段）：
- **A3** = head→1 条 channel（不切片，其余闲）；**A3a** = A3 + 写掩码；
- **A3b**（新）= + head 切片（chunk 在 `16/heads_per_hbm` 条内轮转）；
- **A4** = A3b + master/diff 分离（修正行进 diff channel）；
- **A4b**（新）= + 全局 co-read placement table（丢固定切片，co-read 的 chunk 摊到
  15 条 master channel）；A5/A6 建在 A4b 上。

**实现**（`src/workload_runner.py`）：`_layout_channel_loads` 出每档各 channel 负载；
`_append_placement_pim_scan` **给每条活跃 channel 造一条真实 run 交 Ramulator 逐 run
计价、跨 channel 取 max**（能量 per-run 求和 × num_hbm_used）。
- **一次返工**：中途先写成"probe 单探针 × 负载"外推——chenyi9 指出 **Ramulator 不能省、
  且破坏公平**（线性外推夸大 A3 单 channel 惩罚、能量抹平了 row-conflict 的 ACT）。
  已改成真实 per-channel run，公平恢复。
- **energy `by_layer`**：每层都出条目、缺的填 0（`_energy_breakdown`）。
- 4 个 PIM-scan 站点（decode plain/batched + prefill）都接入;`NoReuseKVLayout`(A1)加
  `layout_policy="slice"`;warm==cold 一致。

**验证**：全量 **61 单测全绿**（新增 `tests/test_placement.py` 20 个；修 7 个过期
testbench 的旧 pool0-14/per-run 语义→新 per-channel；14 个缺文件用 `tests/fixtures/`
修好）。wl_tiny 8 档端到端跑通;`num_hbm=16` 70s、`num_hbm=1` 单 channel trace 大、
冷缓存慢（运行指南加了预热阶段）。

**解析引擎**：按"从不单独出数"裁决,`ablation.py` 不建模新放置,加注说明(A3/A3b/A4/A4b
差异只看 DAG 引擎)。**C++ 评估**:放置模型平凡、无需 C++;修了地址列表内存热点
(按 `_RETAIN_EVENT_ADDRESSES` 门控)。
