## 1. 阻塞：`gen_sweep.py` 生成的 workload 有 9/12 过不了校验

按 guide 起跑，第一批 run 全部秒退：

```
main.py: error: agent 't1n0': must contain exactly one parent_out segment
```

**范围**：12 个 `workload/sweep/*.json` 里 **9 个不可运行**，只有
`wl_broadcast` / `wl_D1` / `wl_pipeline_D4` 能跑——恰好是**每个 agent 只有一个
上游**的三个（`[1,N]` 的下游、单 tier、`[1]×D` 链）。凡是 fan-in / all-to-all
（下游要读**全部**上游输出）的拓扑一律失败。

**成因**：`gen_sweep.py` 对**每一个**上游节点都发一个 `parent_out` 段：

```python
for pid in prev:      # read ALL previous-tier outputs
    segs.append({"role": "parent_out", ...})
```

而 v2-dag schema（`src/workload.py:327-336`）规定一个 agent **有且只有一个**
`parent_out`——它是"声明的那条具体数据依赖"，长度还要和 parent 的 `lout` 相等：

```python
parent_segments = [s for s in request.segments if s.role == "parent_out"]
if len(parent_segments) != 1:
    raise _error(..., "must contain exactly one parent_out segment")
```

`parent_out` 在复用规划里有**特殊语义**（`src/workload.py:461`）：它的 owner
被强制钉为声明的 parent（`owner = (by_request_id[request.parent_id], -1)`），
"即使同 tier 另一个请求有相同输出指纹"也不改——所以它天然只能有一个。

## 2. 修复：沿用已归档 generator 的既有惯例

**不新造语义**。仓库自己已归档的多上游 generator 早就解决过同一问题
（`workload/archived/2026-08-29_pre-sweep/`）：

- `gen_debate.py`：辩手读**自己上一轮**输出用 `parent_out`，读**其他辩手**的
  输出用 `role: "user"`、`sha` 仍是生产者的指纹（`answer_seg(peer, r-1)`）；
- `gen_mapreduce_sum.py`：reducer 对 `map0` 用 `parent_out`，对
  `map1..m-1` 用 `role: "user"` + `sha16(f"map{m}-summary")`。

即 **一个 `parent_out`（声明的 parent）+ 其余上游输出作普通指纹段**。非
`parent_out` 段按 fingerprint 找 owner，`shifted` 由字节偏移差决定
（`src/workload.py:471-476`），跨请求复用照常成立。`gen_sweep.py` 照此改：

```python
parent = (prev[i] if i < len(prev) else prev[0]) if prev else None
segs.append({"role": "parent_out", "sha": sha16(f"out-{parent}"), "len": BLOCK, "delta": 0})
for pid in prev:
    if pid != parent:
        segs.append({"role": "user", "sha": sha16(f"out-{pid}"), "len": BLOCK})
```

`parent` 的选取逻辑（`prev[i]`，越界回落 `prev[0]`）与改前**逐位相同**，
只是提出来复用，避免 agent 的 `parent` 字段与 `parent_out` 的 `sha` 不一致。

**验证**：
- **token 数不变**——只换 role 标签。`t1n0`（alltoall N16/C32）改前改后都是
  1 sys + 1 parent_out + 15 user + 32 doc = **12,304 token**；
- `wl_broadcast` / `wl_D1` / `wl_pipeline_D4` 重新生成后与改前**逐字节相同**
  （它们本来每个 agent 就只有一个上游），说明改动只作用于多上游场景；
- 12/12 workload `--validate-workload` 全过；
- `python3 -m unittest discover -s tests` **61/61 通过**。

## 4. 换机器构建的两个坑（athena，Ubuntu 22.04 / gcc 11）

- **ramulator2**：`CMakeLists.txt` 用 `FetchContent` 拉 yaml-cpp / spdlog /
  argparse，构建节点无外网 → 先把 `ramulator2/ext/` 从本机已有 checkout 拷进来
  再 cmake；
- **cppcore**：`src/cppcore/eventcore.cpp` 只 include 了 `<cstdint>` 却用了
  **非限定的 `size_t`**，gcc 11 直接报 `'size_t' was not declared in this scope`。
  没改源码，用 `CXXFLAGS="... -include stddef.h" make -C src/cppcore` 绕过。
  （要根治就加 `#include <cstddef>` + `std::size_t`，留给维护者定。）

## 5. 集群化运行（机器相关，脚本不入 git）

目标机是 Slurm GPU 集群（6 节点，node1–4 各 96 核、node5–6 各 128 核，
每节点 ~1,007 GB RAM），**约束：本人占用每节点 CPU/RAM 不超过 60%**。
guide 的 `warm_cache.sh` / `run_sweep_models.sh` 是**单机顺序**版本，
这里按同一语义改成跨节点并行，脚本在 `output/_orch2/`（`/output/*` 已被
`.gitignore`，只在本机；见 `RAW_DATA_MANIFEST.md` 的口径）：

- **阶段 1 预热**：**一个模型一个节点**（不同模型 shape 不相交），节点内按
  context 大小分两条流 `[C64]` 与 `[baseline → N64]`，两条流不会同时抢同一个
  shape——保持 guide "**同一 shape 单写者**"的设计意图；
- **阶段 2**：84 个 `(模型, config)` 任务放共享队列，各节点的 worker 槽用
  `mkdir` 原子抢占，**模型之间、workload 之间都并行**；按"最长优先"排序
  （GPT-175B × N-hi 打头）。槽位按 `9 档 × (1+RAMU_WORKERS) ≤ 节点 60%` 算：
  96 核节点 2 槽（54 进程）、128 核节点 2 槽（72 进程）= **12 个 config 并行**；
- **Ramulator 工作目录必须每 job 独立**（`ATTACC_RAMULATOR_DIR` /
  `ATTACC_RAMULATOR_LOG`，`src/system.py:8-12` 已写明理由：CSV 整文件重写）。
  这里再加一条：**计算节点的 `/home` 是 NFS**，trace/yaml 的读写要放**节点本地
  `/tmp`**，只把签名缓存以"每个写者一个分片文件 + 原子 rename"的方式共享回
  NFS 池——避免 NFS 上 O_APPEND 的并发追加；
- **`RAMU_WORKERS` 不能给 1**：`_warm_build_price_finalize`
  （`src/workload_runner.py`）在 `workers <= 1` 时直接 `return None` 退回
  冷路径，build-once 暖流程失效。所以每个 config 的核预算下限是
  `9 × (1+2) = 27` 核。
