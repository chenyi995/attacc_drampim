## 2. F02：A3b 按持久写入序 slot 放置（commit `5e3c564`）

**修改前。** `_striped_append_channel_extents` 的 `slice-append` 分支（`src/workload_runner.py` 旧 916–922 行）
按**本次 scan** 的 unit 序号轮转：第 u 个 unit 落 `(base + u % stripe)`。后果有两个：

- 同一个 chunk 在不同 scan 里落到不同通道（只读 seg2、seg3 的 scan 把它们放到 ch0、ch1，
  全读时却在 ch2、ch3），没有任何存储能做到这一点；每次 scan 都完美均衡，存储也做不到。
- A4c 在 2026-09-04 已改成持久表 `_place_master_by_slot("append")`，A3b 没改，
  于是 A3b → A4c 的差不只是 diff 聚合，master 放置也变了，claim 1 的归因不干净。

**修改后。** master 走与 A4c 同一张表 `_place_master_by_slot("append")`（`_chunk_slot_table(mode="append")`，
第 i 个写入的 chunk 落 slot `i % stripe`，之后每个 scan 都查这张表）。
修正没有 diff 区可去，仍留在同一条轮转里：按 `(owner, fingerprint)` 分组，
`tlb.chunk_slot("diff:<owner>:<fp>", stripe, "append")` 在首次出现时追加到表尾，之后持久；
每组的物理连续 run 由 `tlb.scan_runs` 给出，每个 run 一个 row 对齐 extent。
同一 head 一轮里一起产生的修正仍是一段连续 append（chenyi9 2026-09-03 裁决），注释里的算例原样保留。
无分配器（probe / 单测）时保持旧的按 scan 轮转，`_place_master_by_slot` 本来就这样回退。

**简化（推测，未按真实写入流验证）。** 修正的 slot 顺序是"所有 master chunk 之后、按首次被扫描到的顺序"，
不是真实单流里 chunk 与修正交错的写入顺序。选它的原因是 chenyi9 对 A4c 的定义是"master 不动"：
A3b 与 A4c 的 master 必须落同一通道，A3b→A4c 只差 diff 去向。若用 `NaiveKVLayout.finalize`
的 16 通道页轮转（含修正的真实写入序）做 slot，master 会随修正数量错位，与 A4c 不再同表。

**回归测试。** `tests/test_placement.py::test_a3b_chunk_keeps_its_channel_across_scans`：
同一分配器上全读与只读 seg2/seg3 两次 scan，seg2/seg3 都在 ch2/ch3，ch0/ch1 为 0；
`master-diff-local-append`（A4c）对同一读集给出同样的 master 通道。
既有 `test_a3b_cost_is_monotone_in_k`、`test_worked_example_a_b_c_d_e_f` 不变、仍过。

## 3. F04：fresh prefill 按档选边（commit `79fbc76`）

**修改前。** `run_cacheblend_dag` 里 `if not reusable:`（旧 4196 行）无条件把无复用行的层放到 GPU，
不看 `pim_prefill_mode`。A5（`prefill_attn: pim`）从没把一个 fresh 请求的 prefill 放进 bank；
A6 的选边器从没见过 fresh 请求，`pim_prefill_sides` 里没有它们。

**修改后。**

- 把可复用分支里的选边代码原样抽成 `_resolve_prefill_side(...)`：`gpu` / `pim` 照给；
  `dynamic` 用同一套模型给 xPU 侧（回读 + 整段 GPU attention）和 bank 侧
  （最忙通道的 sweep × 次数 + Q/ctx 链路）定价，`t_bank <= t_xpu` 选 PIM，
  每个请求只在第一次遇到的层决定一次，记入 `dynamic_prefill_sides`。定价公式一个字没改。
- fresh 层先调 `_resolve_prefill_side`（resident 集为空）：
  - `gpu` → 新函数 `_append_gpu_prefill_layer`（见 §4），事件名从 `gpu_score/softmax/context`
    改为与复用分支 GPU 侧一致的 `gpu_prefill_*`，并显式 `op.numOp = heads`
    （模板 numOp 为 `num_heads/tp × batch`，batch=1 时相同；未单独做数值等价核对）。
  - `pim` / `dynamic→pim` → 不再短路，落入下面的拆分路径：`old_reads` 为空、`writes` 为全部 fresh 行，
    走 A5 同一条 bank-whole 路径（`dram_store_diff_and_live` → sweep → `die_score_assembly` → `ctx_pim_to_gpu`）。
    不伪造 resident 回读，注释里的原意保留。

**回归测试。** `tests/test_workload.py::test_fresh_prefill_follows_the_rung_prefill_side`：
纯 fresh 请求在 `gpu` 下有 `gpu_prefill_score`、无 bank scan；在 `pim` 下有 bank scan 与
`die_score_assembly`、无 `kv_pim_to_gpu`、GPU 侧行数为 0；`dynamic` 下 `pim_prefill_sides` 含该请求，

## 8. 追加（同日深夜）：`num_attacc` 记账 bug 与重跑

**起因。** chenyi9 要求在 822 上跑一个最快的小模型 + 小 workload 看 TBT / E2E / 功率。
第一轮（CACHEBLEND-TINY，1 GPU + 1 HBM，多轮多 agent workload，R=8 轮 × 2 chunk，8 个 reuser，
lout 128）里 A5 的能量是 A3b 的 1.93 倍，chenyi9 追问为什么（"减少了搬运，in-bank 能量有上限"）。

**原因（bug，不是物理）。** `main.py` 调 `make_pim_config(...)` 时没有传 `num_attacc`，
它停在默认值 8；而 `PIM.get_time_and_energy[_runs]` 把每项 PIM 能量（DRAM 读、MAC、链路、SRAM）
都乘 `num_attacc`。GPU 侧乘的是 `num_xpu = --ngpu = 1`。于是 1 GPU 的运行里所有 PIM 能量被放大 8 倍。
这是审计 `README_audit_fixes.md` §3.2 已列出、未修的一项（"不再额外套默认 NUM_ATTACC=8"）。

**修复（commit `fc0216d`）。** `make_pim_config(..., num_attacc=num_gpu, ...)`：一块 GPU 配一台 AttAcc，
与 GPU 侧的 `num_xpu` 同一口径。单测 108/108。

**修正后的物理解释（用第一轮 JSON 手算，PIM 类能量 ÷ 8）。**

| 项 | 数值 |
|---|---|
| A5 prefill bank 扫描能量 | 报表 12.19 J → 实际 1.52 J = DRAM 读 1.34 + MAC 0.19 |
| A3b GPU prefill attention（score+softmax+context） | 2.02 J |
| 每 (query, key, head) 对 | PIM 0.33 nJ，GPU 0.44 nJ |
| 第一性原理：MQ n=8 时每对 DRAM 读 | 512 B ÷ 8 × 4.4 pJ/B ≈ 0.28 nJ（与 0.29 nJ 实测一致） |
| 修正后总能量 A3b / A5 | 4.76 J / 3.99 J（A5 少 16%） |

MAC 能量两侧同一常数（0.32 pJ/MAC），差别全在存储访问：PIM 每 8 个驻留 query 把 KV 从 cell 读一遍
（GEMV buffer 512 B = 8 个 Q slice），GPU 每个 L2/L1 tile 的 query 只从 HBM 取一次 KV、其余走 SRAM。
chenyi9 说的 8 tCK 对 6 tCK 是 MQ 命令的**功率**钳位（每个命令窗口的能量预算），拉长的是命令间隔，
不改变总能量；总能量 = 读出字节 × 每字节能量 + MAC 数 × 每 MAC 能量。
第一轮全部数值作废，按 chenyi9 指示重跑。

**重跑约束（chenyi9 裁决）。** ≤ 64 核、≤ 500 GB；监视器按整机实际占用（MemTotal − MemAvailable）
10 s 滑动平均，超过 700 GB 时只 kill 本批运行里 RSS 最大的一个进程，保持整机在 700 GB 内。
实现：`scratch_0905/mem_guard.sh`（每秒采样，日志 `guard.log`），队列 `run_queue.sh`
（两两并行：R8C2N8_L128 + A6 探针 42 核；R16C2N16_L128 + R8C2N8_L1024 62 核）。结果另记。

## 9. 追加：A6 选边为什么反了 —— GPU attention 用的是 legacy 模型

**现象。** 加了 `KVPIM_PREFILL_SIDE_LOG`（commit `681196c`）后看到选边器的两侧价格：
有驻留上下文的请求 `t_xpu / t_bank` 恒为 2.0–2.2，与新算行数 m 无关；独立新 prompt ≤ 512 token 选 GPU、
≥ 1024 选 PIM。chenyi9 指出这与常理相反（prefill token 少该选 PIM、多该选 GPU）。

**原因。** 阶梯脚本没有传 `--gpu-model`，`main.py` 默认 `legacy` = AttAcc 原版 xPU 模型：
S = QK^T 落 HBM、softmax 单独读写、attention 有效算力只有 ~11 TFLOPS（A100 峰值 312）。
用系统对象直接给同一批形状定价（`t_bank` 取自选边日志）：

| 形状 | legacy t_xpu | flash t_xpu | t_bank | legacy 选 | flash 选 |
|---|---|---|---|---|---|
| 独立新 prompt 4352 | 7068 µs（11 TFLOPS） | 476 µs（163 TFLOPS） | 3389 µs | PIM | GPU |
| reuser m=2416, n=6512 | 5871 µs | 459 µs | 2700 µs | PIM | GPU |
| 独立新 prompt 512 | 99 µs | 28 µs | 102 µs | GPU | GPU |
| 独立新 prompt 1024 | 391 µs | 45 µs | 354 µs | PIM | GPU |
| 短 query m=8 于 n=4352 | 95 µs | 85 µs（memory-bound + 回读） | ≈ 1 个 sweep ≈ 10 µs | PIM | PIM |

`flash`（chenyi9 2026-08-21 决策引入：FA-2 融合核，S 不落 HBM）下，选边正好是常理：
新 token 多的 prefill 算力密集 → GPU；在长驻留上下文上只加几个 token（decode 形状）→ PIM。
`legacy` 下 GPU attention 比 bank sweep 慢一倍，所有形状都选 PIM，A6 ≡ A5，且 A5 的 1.8× E2E 被夸大。

**待 chenyi9 裁决。** 阶梯是否统一改用 `--gpu-model flash`（脚本已加 `GPU_MODEL` 透传，commit `8eb562a`）。
改了要全部重跑：A1–A4e 的 GPU prefill 变快，A5 可能输给 A4e，A6 应同时胜过两者——这才是论文的 claim。
