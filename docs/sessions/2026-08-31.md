# 2026-08-31:引擎提速(逐字节等价)+ sweep 的内存可行性边界

本页由**接手跑批的 AI**记录。凡涉及口径的地方沿用仓库既有惯例;
标了"用户裁决"的是 chenyi9 当天的决定。

## 1. 提速:两轮改动,都以逐字节等价验证过(已提交 `98bd6ee`)

### 第一轮(收益小,但消除了一个真实缺陷)

`KVBlock.token_offset` 用 `tuple.index()` 线性扫描,而 `locate()` 会把一个
block 的每一行都走一遍 → **O(L²) 每 (请求, 层)**。`rows` 在全部三处构造点都是
`tuple(sorted(<set>))`,所以连续性快判 + `bisect_left` 返回**同一个下标**。
真实数据核对:352/352 个 block 升序、无重复、且全部连续。

**实测只值 5.6%**(A1 档,其余档在噪声内)。

### 第二轮(收益大,来自用户的物理直觉)

用户指出:**decode 第 n+1 步只比第 n 步多一行 KV**,不该每步重算整段历史。
全程 profile 证实 decode 循环占 **83.4%**,其中每 (输出 token × 层 × 请求) 都在
重建长度 L 的列表、重做 O(L) 的 physical-read 展开、重算与 output_row 无关的
`_prefill_location_deltas`。改成跨步携带状态后:

| run | HEAD | A+D | |
|---|---|---|---|
| LLAMA-7B / wl_D1 / A1 | 3884s | 2908s | −25% |
| GPT-13B / wl_N4 / A1 | 2567s | 2003s | −22% |
| GPT-13B / wl_N4 / A4 | 1742s | 1354s | −22% |

**九档全部受益**(第一轮只有 A1 动),因为 decode 循环是所有档共用的。

另加 `KVPIM_NOGC=1`(默认关):关掉循环 GC 再省约 16%,结果逐字节不变。
**大模型的槽不要开** —— 不回收引用环会多占约 100G,换来的并行度损失大于 16%。

### 验证口径(用户要求:必须真实 DAG 运行,不用解析引擎估计)

36/36 参照 run 逐值等价:27 个汇总报告比字节;9 个**完整事件流**(每个约
25 GB)经 FIFO 流式 sha256 比对(不落盘,共享卷当时 98% 满)。61/61 单测。

## 2. 一个方法学教训:不要用运行的前缀去代表整体

第一次 profile 只采了 900 秒,而建图要 2000+ 秒,TLB 绑定集中在**早期** →
`token_offset` 被报成 14.6%,实际只值 5.6%。**采样必须覆盖全程**,否则占比
是采样窗口的函数,不是程序的性质。

## 3. sweep 的内存可行性边界(本轮最重要的发现)

**内存与 decode 工作量线性相关**,实测两点(22.7 / 24.6 GB per unit)一致:

> `预测常驻内存 ≈ 40 + 25 × W`,其中 `W = 输出 token 数 × 层数 × (总 token / agent 数) / 1e9`

据此,**最大的几个任务在本机放不下**(单节点 1008 GB):

| 任务 | W | 预测内存 | |
|---|---|---|---|
| GPT-175B × N-hi | 52.0 | ~1340 G | 超单节点 |
| LLAMA-65B × N-hi | 43.3 | ~1120 G | 超单节点 |
| LLAMA-33B × N-hi | 32.5 | ~850 G | 需近乎独占 |
| GPT-13B × N-hi | 21.7 | ~580 G | 勉强 |

一个任务不能跨节点拆分(9 档已并行,单档建图是单线程),所以这不是调参问题。
表现出来是**活锁**:N-hi 被领取 → 撑爆节点 → 被杀 → 因"最长优先"又被第一个
领走 → 循环,3.5 小时零完成。

**用户裁决(2026-08-31)**:**N-hi 只保留两个小模型(LLAMA-7B / LLAMA3-8B),
四个较大模型的 N-hi 停放。** 调度模拟显示这与"全砍 N-hi"的 makespan 完全相同
(15–21h),因为长杆变成 `GPT-175B × D-hi` 10.6h —— **保留那两个是免费的**。

**科研代价(需在方法一节说明)**:N 轴(扇出度)的高端点只在两个小模型上有,
而大模型恰是 `heads_per_hbm` 最小、A4 固定切片 vs A4b 全局 co-read 放置表
区分度最高的一端。若这条结论重要,可考虑给大模型做降规模的 N-hi(如 64 个
agent 而非 128,W 减半)。**待裁决。**

## 4. 时间模型(实测标定)

`建图秒数 ≈ 122 + 2135 × W`。用 W≤1.11 的小配置拟合,外推到 W=7.17
(`GPT-175B × supervisor`,6.5 倍外推)预测 5.03h、**实测 4.28h,差 15%**。

## 5. 编排的教训(governor,`output/_orch2/`,不入 git)

三个都是**控制变量选错**,记下来免得重犯:

1. **用槽数控内存**:任务的 RSS 在整个生命周期持续增长,按槽数限制拦不住;
2. **用当前内存做放置判据**:刚放下的槽还没长起来,下一轮又看到"有空间"
   → **同一块空间被反复分配**。必须按**预测的最终占用**记账;
3. **闸门阈值设在红线以下太多**:红线 80%,DRAIN 设在 74% → 节点自然运行在
   77% 就每轮排空一个槽,而排空不会立刻释放内存(要等任务结束)→ **自激收缩**。
   必须留滞回,且只在真正接近红线时动。
