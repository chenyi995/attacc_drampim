## 为什么这样设计

### GPU 名称必须对应实际代码

用户称为 H200，但当前工作区只支持 A100a、H100、B200。新增配置是 B200，且尚未进入起始 HEAD。直接给另一台机器 `--gpu H200` 会在入口失败；仅同步起始 commit 也会遗漏 GPU 修改。因此指南明确写 B200、要求同步包含该修改的源码，并在准备阶段检查 GPUType。没有把 B200 改名为 H200，也没有自行增加 H200 参数。

更快 GPU 的收益不能按峰值算力比例外推。准备脚本调用现有 GPU 计价入口，对实际 LLAMA3-8B 小 batch 的 FC、NORM、ACT 服务工作求和；GPU 分项、内存带宽和总和写入静态证据。它说明 B200 确实有缩短这部分工作的模型依据，也说明 H100 在本配置下的改变较小。GPU 预算不是 PIM 价格，不用于替代 Ramulator，不直接当作流水中的关键路径时间。

### 最小输入保留真实机制

- D4_diff 保留真正的 parent 多轮：每轮读两个新共享文档、继承旧修正、追加自己的输出。后台私有笔记形成明确写入周期。A3b 同轮两份修正正常合并，跨轮分散；A4c 对相同修正跨轮收拢。这个输入不依赖尚未实现的半列追加。
- E2_hot 只需要两篇同时读取的文档。分组导入与周期取文档使朴素放置自然撞通道，当前软件表确实将它们分开；地址来自现有账本，没有手动改 baseline 的地址。
- E2_balanced 只改变选中文档，保留相同规模与导入，说明朴素布局本来分散时收益应减小。对照仍可能受到小块历史和 diff 放置优化，不要求结果严格为零。

短输出用于减少重复 decode 模拟，不声称它与长输出 W1 的累计历史等价。三个输入是机制控制，不代表真实业务分布平均收益。D4 的 A4e 静态列工作也未必优于 A4c，指南保留全部静态结果，没有强行制造逐档递增。

### 公平比较与出表

每份输入内部，两个硬件对照组分别使用同一 GPU、PIM、链路、FlashAttention、pipeline、精度、k 和批量上限。扫描必须按最长 channel 的真实服务时间归并。只换 GPU 时，出表脚本额外核对同一档的 PIM 地址与服务时间签名；若签名不同，将差异显式保留为待解释结果。

末轮汇总请求在实验前就确定。出表对齐其 TBT 与后续生成位置的 scan/GPU 事件，剔除首个生成位置，防止拿不同阶段的百分比相除。同时保留全请求 TBT、TTFT 和包含 owner 导入的 E2E。GPU 共享事件不按 batch 人数人为折半或均摊；GPU 服务总量也不冒充不可隐藏的非 scan 延迟。

指南的性能矩阵只执行相应的布局相邻档与两种 GPU，使用短输入、逐档运行、独立结果目录。原有大 workload、完整 sweep 和 A5/A6 实验不被本次指南替换。

## 验证与证据

1. 从新指南提取所有 bash 代码块，逐块 `bash -n`；内嵌 Python 用 `ast.parse` 检查语法。
2. 执行指南中的准备代码和源码一致性检查。生成小 JSON 后，用当前 `load_workload`、`build_reuse_plan` 与三档真实物理账本检查地址；每个汇总请求的逻辑长度、修正、新旧 diff、重算量和实际物理 token 读量在三档一致。GPU 预算由当前 `xPU` 公式生成。未调用原有 handcheck 主函数或旧 revision 的 runner。
3. 静态数表由 Python 读取上述结果自动写入指南；没有手抄或用行数拟合 PIM 时间。生成代码保存在指南的代码块中，另一台机器会得到 inputs、manifest 与包含完整 extents/GPU 分项/source hash 的 static.json。
4. 出表代码用单独的合成格式样本验证：不等长 channel 确认使用 max；刻意加长的首生成位置确认被排除；检查 TBT 分母、GPU 事件累计及跨 GPU PIM 签名。这些样本只验证报表算法，不是模拟性能，不进入指南的实测表。

本机临时复核材料：`/tmp/fugue-minimal-layout-guide-validation/` 保存真实小输入与静态证据；`/tmp/fugue-minimal-report-contract-only/` 明确标为合成格式验证。长期复现依赖指南内代码和生成产物，不依赖这些临时路径。指南的性能命令与真实报告出表尚待执行机器运行，当前不能承诺 TBT 降幅。

## 追加：按用户指定的路径图、热点图和 bank 吞吐出图

chenyi9 决策：最终用小例子配数据说明问题；路径图每列表示一个 channel、每格表示其中一个 row，每种扫描用不同颜色；热点图以一条分格横带表示各 channel 负载；同时给 scan/TBT 改善，以及 A4e–A6 的 TTFT 和 bank 内算力改善。

实际变更：

- 在指南第 7 节写明各图的坐标、颜色、分组、指标、原始数据和运行方法。当前几何是八 channel/head，因此真实数据画八列，用户举例的四列没有被当作修改硬件的决定。路径图多色条表示同一个 row 被不同扫描访问，不表示半列存储或 DRAM column 占用；箭头只是 diff 子集的地址次序，不冒充 Ramulator 周期轨迹。
- 新增 `docs/experiments/plot_minimal_layout.py`，只读输入、物理账本与已有报告，不调用仿真。它生成两张静态图，并仅在相应真实报告存在时生成性能图。
- `docs/experiments/minimal_layout_figures/` 保存本次真实账本的路径图、静态列请求热点图，均含 PDF/SVG/PNG、CSV 和来源 hash。当前只生成这两张静态图，没有性能曲线或伪造的测量值。
- 新增文档内的 P4 生成/运行步骤：单个单行文档的 owner 加两轮汇总，后续只计算四个新 token。它补充 A4e/A5/A6 的 TTFT 与 bank 指标，不扩展原 D4/E2 数据量。P4 已用当前复用计划静态核验，数表由脚本读取结果写入指南。

为什么不直接画“完全均衡”：当前 E2 只共读两个大文档，A4e 将它们放到两个通道，小块历史另行分散；这不是八个通道承担相同负载。图共用统一色标，保留热点对照和均衡对照，避免靠独立归一化或改颜色夸大收益。

为什么区分算力指标：A4e 的 prefill 在 GPU，bank-prefill 有效吞吐必须是 N/A。相同末轮 decode 在三档均走 PIM，因此主图用该阶段的有效 QK+PV 运算数除以真实 bank 服务时间，才可报告相对 A4e 的倍数；prefill bank 吞吐另存 CSV。A5/A6 的 bank 硬件一致，A6 的新收益来自逐请求选边，不能称作再次提高 PE 峰值。配置频率与有效 GFLOP/s 分开记录。

实际验证：

1. 重新核对全部指南 bash/Python 代码块语法，并执行 P4 静态构造。没有执行指南中的性能循环。
2. 运行新绘图脚本生成静态路径/热点 PDF、SVG、PNG 和原始 CSV；实际查看两张 PNG，确认扫描颜色、物理行号、八列、热点共用色标与静态数据标签。
3. 用独立的小合成事件验证 bank 吞吐算术：每个 sweep 取最慢 channel、不同 sweep/层的工作和时间匹配、因果位置只计一次、decode 排除首生成位置、没有 bank 工作时保留 N/A。合成数据只用于验证公式，没有写入展示图或实际结果文件。
4. 模拟器、preset、trace generator 和已有 workload 源文件仍未修改；新代码仅为图表辅助脚本。性能图和实际提升数值仍等待另一机器执行小输入后生成。
