# 2026-08-27:head→HBM 重映射日(chenyi9 裁决记录)

## 发现:head↔channel 映射不自洽(R18;全文 `../README_head_hbm_remap.md`)

- 起点是 chenyi9 连环追问("一个 head 一个 hbm 下面的 chunk 才能分
  开"、"256 token 是多少 bank 的一个 dram row?"、"一个 channel 到底
  多少 bank?"),把 trace 层与 TLB 层对同一批 channel 的两套解释顶
  了出来:
  - **trace 层**(AttAcc 上游语义):一个 head 一个 **channel**,
    `lch * HBM_GS['ch']` 逐 channel 复制同一列样式;
  - **TLB 层**(本仓布局):token 块按 channel **条带化**轮转。
- 7B/TP8 退化定量:`numOp=4`、`num_hbm=5` →
  `n_head_per_hbm = ceil(4/5) = 1` → legacy 路 `valid_channel=1`
  (单 channel 扫全 L,15/16 channel 闲置;实测 L=256 的 64 条
  MAC_AB 全落 channel 0);池路 15 channel 各复制同列 = 15 个幻影
  head,能耗虚增 ~15×。
- **归因(git 考古,chenyi9 指令"这个错误是哪个 commit 留下来的?
  谁的 commit?")**:三层叠加——放置规则本体 `c1540de`(jwchoi,
  AttAcc 上游 initial commit,2024-05-06,对上游自身配置自洽);带进
  池化/复用路径 `47ae0c3`(xw338,2026-08-21,`ch_delta`/`pool_base`
  保留 lch=head 复制语义);退化配置下出数未察觉 `fb9fabe` 起本线
  (chenyi9)实验链(2026-08-22 起)。

## 修复:head→HBM 条带重映射(裁决:chenyi9,"按照 head 一个 hbm
的重映射改好,先改好,再跑")

- 规范:一个 head 住一个 HBM;run 的各 channel 载该 head **自己的
  token 条带**,`stripe_width = channels // heads_per_hbm`、
  `L_per_channel = ceil(L/stripe_width)`、`num_itr = 1`;head 并行 =
  trace 外 HBM 并发(通式 `heads_per_hbm = ceil(local_heads/num_hbm)`,
  本配置 = 1)。chunk 几何不变(256 token = 64 bank × 1 row,
  32+32 MAC_AB),只是摊上 16 channel(每 channel 串行深度 64→4)。
- 改动:trace 生成器加 `--head-hbm-stripe`(默认关,旧语义逐字节保
  留);wrapper 恒传该旗标、签名加版本记号 `hbmstripe1`、缓存轮换
  `signature_cache_v2_headhbm.jsonl`(旧 ~75 万行留盘归档不载入);
  workload_runner 落 KV 事件改 **per-HBM 带宽份额**、D_i 位图按
  **广播**计(die 侧 q/tuple 聚合/聚合自洽,不动)。
- 实现教训:第一版把缩 L 放 `Attention()` 内部,拼装环仍用原 L 推
  `length` → 大 L IndexError;改为 `run_attention` 顶部缩,生成与
  拼装同一个 L。
- 验证:trace 对照(旧 64 MAC_AB@ch0 → 新 4×16,总量守恒);
  L∈{256,1024,8192,30000}/池/MQ/相位全过;单测 41/41
  (测试桩 PIM 无 `num_hbm`,记账处 `getattr` 兜底)。
- **影响:2026-08-27 之前全部 PIM 侧输出作废**(fig:motiv 套件、
  wl_tiny 阶梯、star r3 全表等);GPU/链路侧不受影响。

## 夜 3:k 轴在 16-HBM 下的再分析(chenyi9 追问"现在 k 有影响了吧")

结论:**有,但走 prefill 选边轴,且方向与 A3 相反——A3a−A6 随 k
收窄,A3−A6 随 k 拉大,两条线在 k* 处交叉。**

- **decode 轴仍 k-平**:掩读下 A3a/A6 扫描字节同为 ctx×(1+k/256),
  同乘相消;序列切分把两档一起 ÷4(7B@16),中段 tier 的 A3a 扫描
  (~57÷4 ≈ 14 µs/层)也钻进 15.7 µs 的 GPU 地板 → decode 轴的
  A3a/A6 差距在 16 HBM 下反而压缩,只剩深 tier 残留(t9 ~×2.2,
  原 ×3.9 渐近比被地板截断)。
- **prefill 翻边点被 16 HBM 推进扫描范围正中**:选边两侧不对称变化
  ——PIM 路每趟全域扫 ÷4(~1.1 µs/层 @16k),GPU 路整段读回走
  NVLink **不变**(~55 µs/层)→ 阈值 m* 从 ~100 行升到 **~400 行**,
  除以位移块数(30–48)得 **k* ≈ 8–16**,正落在 {2,4,8,16,32} 中间:
  k≤8 A6 选 PIM(prefill 轴对 A3a 拉开 ×2–8),k≥16 翻 GPU
  (prefill 合流,只剩 decode 残留)。
- **GQA 档(LLAMA3-8B)k* 落回 ≈2–3**:读回按 KV 头折减(÷4)使
  GPU 路变便宜,PIM 每趟 ÷16 被"容量 8÷组 4 = 每趟 2 成员"抵掉
  一半;GQA 的 A3a/A6 prefill 区分只在 k=2。decode 比值与 MHA 相近
  (复制 ×4 与 sweep ×4 相消)。
- **可验证预言(更新)**:7B@16 套件 `prefill_side_census` 的 A6 列
  应 k≤8 以 pim 为主、k≥16 翻 gpu 为主;GQA 套件几乎全程 gpu
  (k=2 混合)。两条在跑的套件链可直接对数。

## 夜 5:RTL 对簿——能量钳位入模,PC 默认开,全部重跑(裁决 chenyi9)

- **对簿结论(chenyi9:"看看是你算的对还是他算对了")**:RTL 侧对。
  `kvpim-rtl/docs/Fugue-asplos2027` 用与仿真器同源的能量常数证明:
  PC 的 6-tCK 地板本质是**每窗口能量预算**(E₆ = 140.8+5.23 pJ,
  n=1 命令顶红线),n=8 的 MQ 命令 E_cmd ≈ 176–183 pJ → 间隔必须

  6 tCK 不可达,平衡点 PE 时钟 **f\* = 1/tCK = 1.3004 GHz**(每命令
  拍恰一次 MAC,ASAP7 可综合,+3.2% 面积)。仿真器现行 C 模型缺此
  项且 preset 1.733 被 ceil 罚成 7 tCK——双重偏差。**注意:这不是
  推翻 R1**(当年删掉的"等功率摊平"仍然是错的);窗口预算钳位是
  另一形态,且有综合证据。
- **落地(R19)**:`mq_interval_cycles` 增 PC 能量钳位(ê 保守 1.0,
  n=8→8、n=1→6、NPC 不动,六组关键值单测口算验证);A5/A6 preset
  1.733 → **1.3004 GHz**;`--powerlimit` 改 BooleanOptionalAction
