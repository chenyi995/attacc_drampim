# 给chenyi9的输出格式规范(OUTPUT_SPEC,2026-08-22 定稿待审)

本规范约束**一切写给chenyi9看的产出**:回复、README、audit、实验报告。
它是仓库根 `CLAUDE.md`"每一次的输出"三条的细化与可检查版。
写任何文档前先过一遍本页;写完用 §6 自检清单逐条打钩。

## 1. 读者假设(每份文档开头必须声明)

- 默认读者:**计算机专业学生**——会编程、懂矩阵乘法、学过体系结构课,
  但**不了解**本项目,也不了解 LLM serving / DRAM 内部结构 / PIM。
- 因此:凡是课本之外的东西都要讲;凡是本项目自造的名词、编号、缩写,
  第一次出现**必须就地定义**,不能指望读者翻过别的文档。
- 文档开头一句话写明"目标读者 + 读完能回答什么问题"
  (参照 `README_fugue_dataflow.md` 首段的写法)。

## 2. 概念与符号纪律

1. **首现即释**:每个新概念、缩写、变量符号第一次出现时就地解释,
   并在括号里给英文原词。例:行激活 (row activation, ACT)、
   列到列间隔 (column-to-column delay, tCCD)、收缩维 (contraction dim)。
2. **公式的每个符号都给含义与量纲**。例:`pe_cycles = ceil(n / (f·tCK))`
   必须同时说明 n=每次列读要服务的查询条数(个)、f=PE 频率(GHz)、
   tCK=DRAM 命令周期(0.769 ns)、结果单位=命令周期(个)。
3. **记号全文统一**,文档开头立一个记号表;与
   `README_fugue_dataflow.md` 的 GEMM 记号(C[M×N]=A[M×K]×B[K×N],
   K=被乘加消掉的累加维)保持一致,不另造。

## 3. 多维度讲清楚(硬件话题的最低覆盖面)

讲一个硬件/性能机制,至少从下面四个维度各讲一遍,并互相印证:

| 维度 | 必须回答的问题 | 例 |
|---|---|---|
| **算子 (GEMM/GEMV)** | 谁乘谁?M/K/N 各是什么?累加在哪个维? | score 是 Q[n_q×128]·K^T[128×L],K 维=d_head |
| **数据摆放** | 操作数物理放在哪(bank/buffer/寄存器)?搬不搬? | K/V 驻 bank,Q 切片驻 GEMV buffer |
| **时序** | 一步花几个什么周期?瓶颈间隔是谁定的? | 列读间隔 = max(PE 吞吐, 功耗地板, 通路地板) |
| **面积/能耗** | 这个机制花多少硅面积/能量?工艺口径是什么? | buffer 翻倍≈面积主项;N28 SS corner 实测 |

不是每份文档四个维度都要长篇,但**每个维度至少一句话交代**,
缺哪个维度要明说"本文不涉及,见 XXX"。

## 3b. 每个实验必须写明论文意义

凡提到一个实验(编号、目录或脚本),必须**结合论文**说明:
它支撑论文哪个论点/哪一节/哪张表,结论如何进入正文
(直接引用数字?支撑设计裁决?排除某方案?)。
实验↔论文的既定映射以 `docs/EXPERIMENTS.md` 尾节为准,不得自造。
没有论文落点的实验要明说"不入论文/已归档/待定编号"。

## 4. 数字纪律

1. **只写真数字**:仓库里实际跑出的、论文原文写着的。每个数字标来源
   (文件路径 / 命令 / 论文章节)。脑补、外推、"大概"的数字不许出现在
   结论句里;若必须估计,单独放"估计"段并写明推导与不确定度。
2. **换算链完整可复算**:任何折算(工艺缩放、能耗换算)把链条一步步列出,
   每步给因子与出处,读者能用计算器复算出同一个数。
3. **区分三种命题**并用词区分:实测(measured)/推导(derived)/悬置(open)。
   悬置的问题列成清单,不许悄悄当成已知。

## 5. 结构与行文

1. **结论先行**:第一节就是答案;推导只留关键步,细节沉到后面的节。
2. **表格放数据,正文放解释**:表格单元格里不写论证;每张表前后必须有
   正文说这张表读出什么。
3. **给算例**:关键公式至少配一个代入真实数字的完整算例。
4. 简练:删掉不改变读者下一步动作的细节;但**可读性优先于字数**——
   不用裸缩写、不用箭头链代替句子。
5. 中文行文,关键术语后括号给英文;代码、路径、旗标用等宽体。
